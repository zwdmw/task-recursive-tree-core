一句人话

  • 连续任务能保持真实现场，不会每次都把世界重置。

从一个杯子开始

先别怕术语：我们真正要解决的是什么？

先用一个生活里最简单的动作，把所有复杂词汇压缩成一句话。

“请把红色杯子放到右边的投放区。”
这句话听起来只有一个动作，但机器人要面对一串现实问题。
对象是谁？ 识别
红色杯子是哪个实体？现场可能有多个杯子，不能只凭名字猜。
目标在哪里？ 绑定
“右边”是哪个区域？需要一个可验证的目标位置和坐标。
路线能走吗？ 规划
中间有没有墙、箱子或其他障碍？拿起杯子后路线是否仍然成立？
动作真的成功吗？ 验证
命令发出不等于杯子被拿起，更不等于杯子最终已经放好。
核心转折
人只说“结果”，系统必须把结果拆成一连串可检查的前置条件、动作和后置证据。

为什么要有控制面

为什么不能让 LLM 直接调用机器人？

直接调用很快能跑通 Demo，但在真实世界里，最危险的恰恰是“看起来跑通了”。

黑盒方式
LLM → robot.move() → 返回 success
  • 模型既决定做什么，又决定怎么做，还可能直接触发副作用。
  • 失败只剩一句“没成功”，很难定位到底是路线、抓取还是验证出了问题。
  • 重试可能重复抓取、重复释放，造成二次副作用。
  • 过程没有统一的任务状态、快照、事务和审计边界。
控制面方式
意图 → 任务树 → 工件 → ActionRequest → Runtime → Observation
  • 每一步都有明确责任人和权限。
  • 每次动作都能关联到任务节点、计划版本和世界快照。
  • 失败先变成结构化 Diagnostic，再决定是否修复。
  • 模型不能越过 Runtime 直接碰后端。
关键区别： 黑盒关注“有没有返回值”；控制面关注“现场是否真的变了，而且变成了预期的样子”。

最简单的任务

最小案例：Place 到底包含多少事情？

用户只说一个“放置”，系统内部至少要回答五类问题。

目标把 cup-red 放到 drop-zone
准备找到对象、确认目标、生成抓取计划
移动先到抓取位置，再拿起，再带着物体走
完成释放、确认已松开、确认最终位置正确
异常路线被挡时，先修复阻碍，再回到原任务
Place=理解目标+准备计划+拿起+携带+释放+验证

注意：这里的“+”不是数学加法，而是说明一个大目标由多个有先后关系的小工作组成。每个小工作都能独立记录成功或失败。

提前规划的原因
系统会在还没有拿起杯子时，先检查“带着杯子能不能走到目标”。如果这时就发现路不通，修复会更安全，因为夹爪还是空的。

三件最重要的东西

整套架构只有三个核心对象要先记住

把这三样东西分开，后面的所有设计就不容易混乱。

任务树 决定下一步
记录步骤、顺序、状态、失败原因和修复分支。它不等于现场，也不等于路线本身。
世界模型 记录现在
记录机器人、物体、障碍物、区域和版本。它只接受观察和世界更新。
规划工件 记录怎么做

最简单的记忆口诀

任务树

什么是任务树？把它当成“会执行的待办清单”

普通待办清单只写要做什么；任务树还记录顺序、状态、证据和失败后的分支。

普通待办清单
□ 找杯子
□ 走过去
□ 拿起来
□ 放下
升级为 →
任务树
✓ 找杯子 证据：cup-red
✓ 规划路线 工件：nav-v1
… 拿起来 正在执行
↳ 失败时挂 repair 子树
节点一个可以被解释、执行或展开的工作。
child 边正常的子任务关系，表示“这个步骤属于上一级”。
repair 边失败后挂载的修复关系，表示“先处理这个障碍”。
状态pending、running、succeeded、failed、blocked 等运行状态。

避免概念混淆

任务树不是日志，也不是一大坨 JSON

这三个东西各有职责，混在一起以后，谁拥有状态、哪个计划过期、失败在哪里都会变得不清楚。

任务树

结构

“应该按什么顺序做？现在做到哪一步？”

由 Kernel 解释，由 Store 保存。

世界快照

事实

“机器人和物体此刻在哪里？现场版本是多少？”

由 Observation 推进。

规划工件

方案

“在 world:0 的条件下，路线和姿态怎么走？”

不可变，按依赖判断新鲜度。
错误想象
{ intent, current_state, plan, result, error, retry }

所有东西挤在一个对象里，看似省事，实际上无法准确判断“计划为什么失效”。

正确的分工
任务树可以继续存在，世界快照可以继续推进，旧工件可以保留作审计；三者不需要互相覆盖。

世界模型

什么是 WorldModel？它就是系统的“现场账本”

机器人不是生活在模型的想象里，而是生活在一个会变化的物理世界里。

world:7 · 当前世界快照
机器人base=(6.5, 4.5)，夹爪已打开，未持物
cup-red位于 drop-zone 中，实体版本 4
drop-zone目标区域，允许误差 0.3
map障碍占用版本已记录
world:0杯子在起点
机器人未持物
每次观察推动版本→
world:7杯子已到目标区
机器人已释放

“世界版本”不是为了让数字好看，而是为了回答：这份计划是根据哪一刻的现场算出来的？在它之后现场有没有发生过会影响计划的变化？

最重要的边界
规划器和 Verifier 读取 WorldSnapshot；它们不能直接读取机器人后端的私有状态，更不能绕过观察把“猜测”写成事实。

模型边界

LLM 能做什么，不能做什么？

这不是削弱模型，而是把模型放在它最擅长、也最容易被约束的位置。

LLM 可以做
  • 理解自然语言目标。
  • 向用户追问缺失信息。
  • 把对象和目标绑定成明确标识。
  • 提交规范化的 TaskProgram。
  • 提出高层任务意图。
LLM 不可以做
  • 直接修改 TaskTreeStore。
  • 直接调用 RobotBackend。
  • 伪造 Observation 或验证结果。
  • 跳过 Runtime 的安全、租约和事务。
  • 把内部算法迭代伪装成业务节点。
权限 模型提交“申请单”，系统决定“能不能执行”。

如果模型给出了一个不合法任务，系统应该拒绝或要求澄清，而不是因为“模型很聪明”就放宽边界。可靠性来自约束，不来自祈祷。

节点生命周期

一个节点从 pending 到 succeeded，究竟经历了什么？

所有节点都经过同一个 Kernel 生命周期。复合节点可以展开，叶子节点可以执行，但最后都要验证。

进入读取目标和当前状态，检查是否已经满足。
前置确认工件新鲜、条件成立、资源可用。
执行 / 展开叶子做工作，复合节点返回 GraphDelta。
后置根据不可变快照和证据判断结果。
失败生成 Diagnostic，可能挂 repair，也可能进入 blocked。
一个容易误解的细节
某个目标已经满足时，叶子节点可以跳过动作；但结构节点不能因为目标满足就跳过必要的展开，否则树形结构和后置验证会失去意义。

案例二 · 为什么不盲目重试

为什么不能简单地“再试一次”？

如果现场条件没有改变，重试只会重复同一个失败；如果现场已经部分改变，盲目重试还可能造成二次副作用。

做法表面上发生什么实际风险
原计划再跑一次继续撞同一条被挡的路线没有改变失败原因
让 A* 偷偷搬箱子路线算法内部产生物理副作用任务树看不到搬箱子，无法审计和验证
让模型自由发挥可能临时调用未授权动作越过安全边界，难以回放
结构化修复先挂 repair 子树搬箱子，再刷新依赖工件原因、动作、结果都可追踪
规则：算法可以证明“移动某障碍后会有路”，但不能在算法内部偷偷移动障碍。物理副作用必须成为任务树里显式的工作。
更直白地说
如果系统搬了东西，却没有在任务树里留下“谁搬的、为什么搬、搬到哪里、是否验证成功”，那它就无法可靠地解释和恢复。

案例二 · 收敛与停止

递归修复会不会无限套娃？不会，系统有明确的收敛条件

“能修复”不等于“永远修复”。真正的工程系统必须知道什么时候停止。

递归深度上限修复任务带有 repair_depth，超过上限就不能继续挂新的修复。
证据门槛没有具体 movable witness、可行停车区和反事实路径证明，就不能提出搬障碍修复。
资源占用限制如果机器人已经拿着杯子，不能再去抓第二个障碍物；应改为重新规划携物路线。
失败收敛重复失败、无安全绕行、无可达停车区时，进入 blocked，交给人工或上层策略。
失败→有证据？→有安全修复？→深度和资源允许？→挂 repair
任一答案为否：不继续猜，明确报告 blocked。
工程上的诚实
一个明确的 blocked，比系统不断尝试未知动作更有价值。它让人知道需要补充能力、改变现场，还是由人工接管。

扩展方式

未来增加新任务、新机器人、新算法，应该怎么接？

扩展点应该落在协议上，而不是把所有逻辑重新塞进 Kernel。

新增高层任务

  • 增加已校验的 TaskProgram action。
  • 只编译根节点。
  • 注册 decomposer，返回 GraphDelta。
  • 复用已有 system operation 和 physical skill。
  • 补端到端测试和树形状断言。

新增机器人

  • 实现 RobotBackend protocol。
  • 把厂商 SDK 类型封装在 adapter 内。
  • 把 telemetry 转成 Observation。
  • 不把厂商私有状态暴露给 planner 或 verifier。
  • 保留 ActionRequest / reconciliation 契约。

新增 MPC

  • 实现 JointTrajectoryController。
  • 注入 backend / controller adapter。
  • 保持 ActionRequest 和 Observation 不变。
  • 不要把 MPC 迭代变成任务树节点。
  • 用安全边界和回放测试验收。
判断标准：新增能力应该改变“局部实现”，而不是破坏“任务树、工件、Runtime、Observation”的公共契约。

第一课 · 心智模型

先只认识四种东西：目标、任务树、世界、工件

如果这四种东西没有分开，后面所有术语都会混在一起。

1. 目标 / Intent“把红杯放到右边”人真正想要的结果。它还没有说明每一步怎么做。
2. 任务树 / TaskTree先规划、再抓取、再移动、再释放把目标变成有顺序、有状态、有验证的工作清单。
3. 世界 / World杯子在哪、箱子在哪、机器人是否拿着东西系统对当前现场事实的版本化记录。
4. 工件 / Artifact基于 world:0 生成的路线和姿态把“怎么做”具体化，并记住它依赖哪个世界版本。
目标→任务树→工件→动作请求→观察→新世界
最容易犯的混淆
“我已经算出了路线”不等于“机器人已经走完了”；“机器人收到了命令”也不等于“目标已经满足”。架构把这些状态分开，正是为了不自欺。
你看到的东西它回答的问题它不回答的问题
TaskProgram用户想要什么？具体哪条轨迹最安全？
WorldSnapshot现场现在是什么样？下一步一定会成功吗？
Artifact按照哪个版本、怎样做？动作后实际发生了什么？
Observation动作后观察到了什么？是否应该直接修改任务树？

第二课 · 设计动机

组件为什么存在：从“会出错的地方”倒推设计

不要把组件看成一堆类名；每个组件都是为了堵住一种具体的错误。

如果没有它，容易发生什么对应组件它具体堵住的错误
模型直接发出任意机器人命令TaskProgram + Compiler把自由文本限制成可校验的任务意图。
多个模块同时修改任务树TaskTreeStore只允许一个 Kernel 持有写入能力。
任务做到一半不知道下一步TaskTreeKernel统一解释生命周期、子节点、验证和修复。
分解器偷偷把节点塞到别处GraphDelta 校验限制挂载范围、父子关系、无环和可达性。
路线还是旧现场的路线ArtifactFreshness比较快照、地图、实体和机器人版本。
系统操作绕过安全层直接碰机器人HarnessRuntime成为唯一物理执行入口。

第二课 · 设计原则

每个组件的高层原则：能做什么，也要知道不能做什么

架构的质量不只靠“它能完成任务”，还靠“它被禁止做什么”。

LLM / Agent只提交意图，不提交副作用可以理解、澄清、选择对象；不能写运行态树，不能直接调机器人。
Compiler先校验，再进入执行世界把 TaskProgram 编成根节点；不把任意外部 DTO 直接当权威运行态。
Store单一事实来源节点规格、运行态、边、执行栈和事件都由同一个 Store 保存。
Kernel唯一生命周期解释器只有它能推进状态、挂载 GraphDelta、处理失败和重试。
WorldModel只记录可观察事实世界版本由 Observation 推进；规划器不能把自己的猜测写成事实。
Artifact不可变，依赖可检查旧工件保留用于审计；世界改变时发布新工件，而不是偷偷改旧工件。
HarnessRuntime副作用集中管理做新鲜度检查、前置守卫、资源租约、事务和观察对账。
Verifier / Repair结果先证据，修复再入树Verifier 不调用规划器；RepairResolver 只能提出方案，不能自己改树。
允许的方向任务树读世界 → 系统操作生成工件 → 技能构造请求 → Runtime 执行 → Observation 更新世界
禁止的捷径模型直接调机器人、A* 偷偷搬障碍、技能直接改状态、验证器自己重规划。

第三课 · 世界状态

世界状态先讲清：系统到底在记录什么？

后面的规划、守卫、验证和修复，都只能基于某个版本的世界状态。

世界模型 WorldModel像一个持续更新的“现场账本”。它接收 Observation，并在内存中维护当前状态。
世界快照 WorldSnapshot像从账本上取出的只读照片。规划器和 Verifier 读取它，但不能直接改它。
版本 revision每次 ingest 一次观察就推进一个世界版本；例如 world:0、world:1、world:7。
事实与计划“箱子在 (4.5, 3.5)”是事实；“从这里走到那里”是计划，两者不能混写。
参考实现的边界
当前参考实现的 WorldModel 和 TaskTreeStore 都主要在内存里；JSON 导出方便检查和回放，不等于已经具备完整的崩溃恢复协议。

第三课 · 实体状态

EntityState：一个物体的状态到底包括哪些属性？

先把一个杯子拆开看；理解了一个实体，理解区域和障碍就容易了。

{
  "entity_id": "cup-red",
  "kind": "object",
  "pose": {
    "x": 2.5,
    "y": 2.5,
    "z": 0.0,
    "yaw": 0.0,
    "frame": "world"
  },

  "tags": ["cup", "red"],
  "properties": {
    "movable": true
  },
  "version": 0

字段白话解释在杯子任务中怎么用
entity_id稳定身份证，不是显示名称任务引用 cup-red；即使展示文案改变，引用仍然稳定。
kind实体大类object 表示物体；region 表示目标或停放区域。
pose位置、方向、坐标系规划器知道杯子在哪里；frame 防止把不同坐标系混在一起。
radius用于碰撞和空间近似的尺寸杯子半径影响可达性、占用格子和载荷包络。
tags语义标签集合可用 cup、red 等标签做选择，不必只靠名字猜。
properties领域属性字典movable 表示可移动；nav_obstacle 表示会挡导航。
version这个实体自己的变化次数杯子被放下后版本增加，旧计划就可能不再新鲜。
为什么不把所有东西塞进一个 description 字符串？
因为规划和验证需要可计算的字段。字符串适合给人看，结构化属性才适合做前置条件、碰撞判断和版本比较。

第三课 · 机器人状态

机器人状态与版本：为什么 state_epoch 不能省？

世界版本告诉你“现场更新过几次”，机器人状态纪元告诉你“机器人自身是否变过”。

world:0 · 空手 
{
  "base_pose": {"x": 1.5, "y": 1.5, "yaw": 0.0},
  "joints": [0.0, 0.0],
  "gripper_open": true,
  "held_object_id": null,
  "state_epoch": 0
}
执行抓取并收到观察 →
world:2 · 已持有杯子 
{
  "base_pose": {"x": 2.5, "y": 2.5, "yaw": 0.0},
  "joints": [0.48, -0.97],
  "gripper_open": false,
  "held_object_id": "cup-red",
  "state_epoch": 2
}
属性记录什么如果忽略会怎样
base_pose移动底盘的位置和朝向导航计划的起点可能已经不对。
joints机械臂当前关节角旧的抓取轨迹可能无法连续接上。
gripper_open夹爪是否张开无法判断能否抓取或释放。
held_object_id当前是否持有某物系统可能错误地尝试抓第二个物体。
state_epoch机器人状态变化的纪元工件无法检测“轨迹起点已变”。
参考模型边界
当前项目里的机器人是确定性的平面双连杆参考模拟器。这里的字段契约可保留到真实机器人，但真实控制器、噪声和在线安全监控仍需另行接入。

第四课 · 观察闭环

Observation 如何推进世界：动作之后才有新事实

把“请求”和“事实”分开，是这套架构最重要的学习点之一。

1 ActionRequest 技能提出：请执行抓取。
→
2 HarnessRuntime 检查工件、守卫、资源和事务。
→
3 RobotBackend 模拟器或真实机器人执行命令。
→
4 Observation 读取夹爪、关节和物体的实际状态。
→
5 WorldModel.ingest 生成下一个不可变快照。

动作前：world:1

robot.gripper_open = true
robot.held_object_id = null
cup-red.version = 0
收到 Observation →

动作后：world:2

robot.gripper_open = false
robot.held_object_id = "cup-red"
robot.state_epoch = 2
cup-red.version = 0
阶段它是什么谁可以改变它
请求ActionRequest：想让后端做什么PhysicalSkill 构造，Runtime 接收。
执行Backend：实际尝试做什么HarnessRuntime 唯一调用入口。
观察Observation：动作后看见什么Backend 提供，WorldModel 接收。
结论Verifier：后置条件是否满足只读快照，返回结果和证据。
关键句
命令返回成功，只说明命令被执行流程接受或完成；只有 Observation 加上 Verifier，才能说明杯子真的被夹住、真的到达目标。

失败类型说明下一步通常是什么
ROUTE_BLOCKED路线被具体障碍物挡住验证可移动 witness，执行递归搬移修复。
STALE_PLAN工件依赖版本不匹配重新规划，不重复执行旧工件。
HOLD_LOST观察到物体不再被持有根据现场事实重新对账或进入人工恢复。
OUTCOME_UNKNOWN证据不足，无法确认结果先观察/人工确认，不能直接宣称成功。
GUARD_FAILED动作前置条件不成立不执行副作用，重新定位或修复前置条件。
两条边界
Verifier 负责判断和给证据，不负责规划；RepairResolver 负责提出 GraphDelta，不负责直接写 Store。这样修复本身也必须被 Kernel 管住。
