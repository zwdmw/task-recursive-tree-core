00 · 先看完整对象链

系统不是一条“抓取 → 放置”脚本，而是十二种标准对象的转换链

每个箭头都表示一次明确的构建或验证边界。上游只能交付约定结构，下游不能越过对象所有者去读取私有状态。

统一生成语法
原始来源→ 规范化器 / 构建器→ schema 校验 + 不变量→ 版本化标准对象→ 下游消费者
本任务字段链
catalog.apple_3.color=green→ EntityQuery(color=green)→ BindingArtifact=[apple_3]→ TaskNodeSpec(manipuland=apple_3)→ txn_87622be3→ scene_000142@rev74
① 场景事实可信目录元数据 + MuJoCo 实时位姿、支撑、夹爪和安全状态
② 场景能力快照scene_capability_snapshot/1.0，给翻译与语义绑定使用
③ 运行时世界快照robot.world_state/1.0，事务一致性读取切面
④ TaskProgram自然语言被改写为动作、查询、约束和目标公式
⑤ BindingArtifact语义查询落到稳定实体 ID，并带候选、证据与读集
⑥ TaskNodeSpec编译后的可执行根节点，含前置条件、目标和重试策略
⑦ Diagnostic三值谓词不满足时生成的结构化失败说明
⑧ RepairProposal修复理由、GraphDelta、工件失效和持久义务
⑨ Planning Artifact不可变布局、路径、姿态及记录级依赖版本
⑩ Action + Transaction类型化请求、读写集、资源租约、幂等派发
⑪ Effects + Reconciliation观察证据提交世界；结果未知时先对账再继续
⑫ Verification Result独立读取最终快照，检查主目标、修复义务和事务闭合
阅读方式： 每一节先横向读四栏，理解“输入怎样变成标准对象”；再纵向追踪粉色的“本次实例”，就能把通用机制与这次绿球运行一一对应。
01 · 两种快照先分清

“场景能力快照”与“运行时世界快照”不是同一个对象

前者是面向任务理解的、坐标弱化的能力投影；后者是面向执行、事务和验证的版本化事实切面。 旧图把它们合并成“世界快照”，导致来源、字段和用途都不清楚。

通用构建式
catalog + support_of()→ build_scene_capability_snapshot()→ scene_capability_snapshot/1.0； committed records→ WorldStateService.freeze_snapshot()→ robot.world_state/1.0
本任务字段链
apple_1 on plate_1 + apple_3 green + box_1 movable → scene_snapshot_c7026126abbc702e@rev1 → 翻译 / 绑定； WorldState records rev1→74 → scene_000142 → 最终验证
1原始输入

能力投影：感知目录中的类别、属性、affordance、movable，以及实时支撑关系。

运行时快照：已经提交到 WorldStateService 的实体、关系、任务、末端、安全和证据记录。

2规范化规则
  • 能力投影不输出控制轨迹，只输出可理解的实体、区域、关系和公开任务能力。
  • 运行时快照不重新推理；它冻结当前已提交记录，形成一致读取切面。
  • 两者都带版本引用，编译前必须检查引用是否仍匹配当前场景。

02 · 世界快照如何规范化构建

先把原始场景变成标准记录，再冻结成事务一致的世界切面

世界快照不是摄像头帧，也不是任意 JSON 拼接。它先经过实体、能力、关系、末端状态、证据和版本规则的规范化， 只有提交后的权威记录才能进入 robot.world_state/1.0。

通用构建式
可信目录 + 实时观测 + 动作效果→ Entity / Relation / EndEffectorState 规范化 → commit_* 写入权威存储 → freeze_snapshot() → robot.world_state/1.0
本任务字段链
apple_3 / plate_1 / apple_1 / box_1 + gripper=empty → 六个 Entity 与初始支撑事实 → 14 次物理派发产生的 confirmed / refuted / unknown effects → world rev 74, frame graph rev 15 → scene_000142
2A原始场景 → Entity / Relation / EndEffectorState
1原始输入契约
  • 可信元数据：body / geom / kind / category / attributes / affordances / movable / geometry
  • 实时观测：实体 pose、quat、support_of、gripper holding、碰撞与安全状态
  • 动作效果：predicate、participants、state、required、evidence_refs
2规范化规则
1实体 ID 只能由系统分配或接受可信目录中的稳定 ID；模型不能自造 ID。
2能力统一为 available / unavailable / unknown；显式能力优先于旧 affordance。
3缺省 freshness：可移动对象用 TTL；固定 workspace 用 scene_epoch。
4谓词参与者使用规范角色，如 subject / region_owner / object / support。
5只有 effect 为 confirmed 或 refuted 才提交关系；unknown 不写成事实。
6支撑关系冲突时，保留新确认 owner，并把旧支撑关系提交为 false。

03 · 自然语言如何规范化为 TaskProgram

“把绿色苹果放在空盘子里”先变成可校验语义程序，而不是直接变成控制动作

TaskProgram 负责表达意图，不包含路线、关节轨迹或机器人私有状态。 它必须引用当前场景能力快照，并把“空盘子”显式保存为可编译约束。

04 · 语义查询如何绑定稳定实体

“绿色苹果”不是字符串替换，而是 Query → Candidates → TaskSlot → BindingArtifact

05 · TaskProgram 如何编译成根节点

编译器把变量、约束与重试策略物化为唯一根 TaskNodeSpec

初始编译不会预先展开整棵 75 节点任务树。它先生成一个确定性根节点， 运行时只有在需要分解或修复时才追加 GraphDelta。

通用构建式
TaskProgram + resolved bindings + predicate registry → TaskCompiler.compile() → 变量物化 + 前置条件 / 目标 / 重试策略 → TaskNodeSpec + kernel tree definition
本任务字段链
$object=apple_3, $destination=plate_1, requires_empty=true → support_region_empty(plate_1)=true → node_38af281a3299， max_attempts=1, max_repairs=3
1原始输入契约
  • 规范化 TaskProgram
  • 两个 resolved TaskSlot / BindingArtifact
  • 当前场景能力快照与 world revision
  • predicate registry 与任务资源前置条件
2编译规则

12 · OUTCOME_UNKNOWN 如何规范化对账

调用超时不等于动作没发生：先禁止重放，再用新观察关闭或继续事务
