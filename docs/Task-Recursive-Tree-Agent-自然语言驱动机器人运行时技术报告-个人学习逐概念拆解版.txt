1. 摘要

1.1 核心结论

可以把这套系统理解为“自然语言驱动的机器人领域运行时程序”，但不能简单理解成“自然语言直接变成机器人控制代码”。

更精确的描述是：

用户用自然语言表达目标；系统把目标规范化为类型化的 TaskProgram；再把它解释成可动态展开的任务递归树；任务树通过带版本依赖的规划工件生成物理动作请求；物理执行结果通过 Observation 回流到世界模型；内核根据证据决定继续、重试、对账、递归修复或终止。

这句话里有三个层次不能混在一起：

| 层次 | 它回答的问题 | 当前系统中的对应物 |
| --- | --- | --- |
| 意图层 | 人到底想让机器人做什么？ | 自然语言、LLM、TaskProgram |
| 任务程序层 | 为了达成目标，需要经过哪些可解释步骤？ | TaskNodeSpec、TaskEdge、任务递归树 |
| 物理执行层 | 机器人现在应该发出什么具体动作？动作是否真的完成？ | Artifact、ActionRequest、HarnessRuntime、Observation |

因此，系统的真正创新点不在于“让模型会说话”，而在于：

1. 把自然语言意图转换成受约束的任务程序；
2. 把任务程序变成有状态、可追踪、可验证的运行时树；
3. 把规划、动作、观察、验证和故障修复纳入同一条执行闭环；
4. 让物理副作用必须经过显式任务节点和唯一物理入口；
5. 让失败不再只是一个字符串，而是可以继续驱动程序演化的结构化数据。

1.2 最简心智模型

可以先记住下面这张图：

自然语言
   │
   │  表达目标、约束、意图
   ▼
TaskProgram
   │
   │  编译成初始任务定义
   ▼
TaskNodeSpec + TaskEdge
   │
   │  运行时动态展开
   ▼
TaskTreeRuntime
   │
   │  读取世界、生成规划工件
   ▼
Artifact
   │
   │  转换成受限物理请求
   ▼
ActionRequest
   │
   │  唯一物理执行入口
   ▼
HarnessRuntime / RobotBackend
   │
   │  执行后必须观察
   ▼
Observation -> WorldSnapshot -> Verifier
                         │
                         ├── 成功：继续或完成
                         ├── 过期：重新规划
                         ├── 失败：诊断
                         └── 可修复：挂载 repair 子树

2. 问题：为什么机器人需要“运行时程序”

2.1 传统脚本能解决什么

在环境固定、对象固定、动作成功率高的情况下，机器人可以执行预先写好的脚本：

move_to_pick_stance()
grasp("cup-red")
move_to_drop_zone()
release()

这种方式简单、速度快，也容易在实验室里验证。但它隐含了很多假设：

- 杯子一定存在；
- 杯子的位置没有变化；
- 收纳区没有被遮挡；
- 规划出来的路线在执行时仍然有效；
- 抓取一定成功；
- 执行器返回成功就代表物体已经放好；
- 任何失败都可以简单地从头再试。

这些假设一旦进入真实场景，就会变得危险。

2.2 机器人任务不是一次函数调用

“把红杯子放到收纳区”表面上是一句话，实际上至少包含：

找到红杯子
找到收纳区
确认对象和目标没有绑定错误
计算适合的抓取方式
找到抓取位置
规划移动底盘路线
规划机械臂接近路径
执行抓取
确认确实抓住了
切换到持物姿态
重新检查持物状态
规划带载荷的运输路线
移动到目标附近
确认可以释放
执行释放
确认物体已经脱离夹爪
确认物体确实位于目标区域

其中每一步都可能受前一步结果和现实世界变化影响。

所以问题已经不是：

“调用哪个机器人 API？”

而是：

“在当前世界状态下，任务现在处于哪一步？下一步的前置条件是否满足？上一步的结果是否有证据？如果失败，失败是否可解释、可恢复？”

这就是运行时的职责。

2.3 为什么自然语言不能直接成为低层控制程序

自然语言具有以下特点：

- 允许省略；
- 允许歧义；
- 同一个目标有多种合理方案；
- 不天然携带坐标、单位、坐标系和版本；
- 不天然表达资源占用和安全边界；
- 不天然区分“命令已发送”和“世界已经改变”。

例如：

“把左边那个杯子放进去。”

系统必须进一步确定：

左边是相对于谁？
“那个杯子”是哪个实体？
“进去”是进入哪个区域？
允许杯子倾斜吗？
如果有两个同样靠左的杯子怎么办？
目标区域是否有容量？
放置后需要满足什么距离和朝向？

因此，自然语言更适合做高层源语言，不适合直接做物理执行指令集。

3. “自然语言驱动运行时代码”的准确含义

这个说法可以拆成三个判断。

3.1 自然语言是源语言：是

用户表达：

把红色杯子放到收纳区，并保持杯子直立。

这相当于告诉系统：

目标对象：一个满足“红色、杯子”的实体
目标区域：一个满足“收纳区”的区域
约束：放置后保持直立

自然语言在这里表达的是：

- 目标；
- 约束；
- 偏好；
- 例外处理意图；
- 对失败的高层解释。

它不是直接规定每个关节的数值。

3.2 任务递归树是领域专用运行时程序：是

任务树中的每个节点不是一段任意代码，而是一个有明确语义的领域操作，例如：

ResolveAndInspect
PlanPick
PlanTransfer
ExecuteGrasp
VerifyHeld
NavigateHeld
ExecuteRelease
VerifyPlaceGoal

节点拥有：

- 任务类型；
- 操作类型；
- 控制类型；
- 来源；
- 参数；
- 前置条件；
- 后置条件；
- 最大尝试次数；
- 最大修复次数；
- 是否允许在目标已满足时跳过；
- 运行时状态；
- 输出工件；
- 最近诊断。

这已经具备程序的核心特征：

有结构
有控制流
有状态
有输入输出
有前置条件
有后置条件
有异常路径
有执行栈
有事件日志

但它是机器人领域的专用程序，而不是通用 Python、JavaScript 或机器码。

3.3 自然语言直接控制电机：不是

真正调用机器人后端的路径被限制为：

PhysicalSkill.build_request
    -> ActionRequest
    -> HarnessRuntime.execute
    -> RobotBackend.execute
    -> Observation

LLM 没有直接获得 RobotBackend，也不能直接修改 TaskTreeStore。

这不是额外的形式主义，而是整个架构能否被信任的关键。

4.2 依赖方向

依赖方向是有意设计的：

任务树决定“下一步做什么”
领域能力决定“这个动作怎样计算”
物理技能决定“怎样把计划翻译成请求”
HarnessRuntime 决定“请求是否有资格触碰真实设备”
WorldModel 决定“现实状态是什么”
Verifier 决定“目标是否有证据证明已经满足”

相反的依赖被禁止：

- 规划器不能直接修改任务树；
- 谓词不能直接调用机器人；
- 物理技能不能绕过运行时；
- 修复器不能直接写入 Store；
- LLM 不能伪造执行结果；
- A*、IK、RRT 不能偷偷移动现实中的物体。

5. 用编译器和虚拟机来理解这套系统

这是理解架构最有效的类比之一。

5.1 对照表

| 机器人 Agent 概念 | 编程语言运行时中的近似概念 | 说明 |
| --- | --- | --- |
| 自然语言 | 源代码 | 表达目标，但可能含糊 |
| TaskProgram | AST / 中间表示 | 已经结构化、可校验 |
| TaskNodeSpec | 函数定义或指令描述 | 静态语义，不记录本次执行进度 |
| TaskNodeRuntime | 函数调用实例 / 栈帧状态 | 记录本次执行的状态和尝试次数 |
| TaskEdge | 控制流边 / 依赖关系 | 表达子任务和修复路径 |
| GraphDelta | 动态加载的代码片段 | 以受限方式增加任务节点 |
| TaskTreeKernel | 解释器 / 虚拟机 | 推进生命周期，解释节点语义 |
| ExecutionFrame | 调用栈帧 | 记录当前节点处于哪个阶段 |
| WorldSnapshot | 外部环境 / 堆状态 | 机器人面对的现实快照 |
| Artifact | 类型化中间值 / 编译产物 | 路径、抓取计划、绑定结果 |
| ActionRequest | 系统调用 | 请求运行时代为执行物理动作 |
| HarnessRuntime | 内核 / 设备驱动 | 唯一受控硬件入口 |
| Observation | 系统调用返回值 | 动作后的现实证据 |
| Verifier | 断言 / 后置条件检查器 | 只依据快照判断 |
| Diagnostic | 异常对象 | 结构化失败原因 |
| RepairProposal | 异常处理分支 | 生成一棵可验证的修复子树 |
| 事件日志 | trace / execution log | 记录程序如何运行 |

这个类比不是说机器人系统真的运行字节码，而是帮助理解职责：

语言模型负责把“想做什么”说清楚；内核负责按规则解释任务；能力模块负责计算；设备运行时负责副作用；观察结果负责把现实带回程序。

5.2 为什么不是一次性编译完整程序

当前核心编译器只编译根节点：

TaskProgram
    -> root: Place

当 Place 节点进入运行时，才由分解器返回子节点：

Place
    -> ResolveAndInspect
    -> PlanPick
    -> PlanTransfer
    -> Pick
    -> TransferHeld
    -> Release
    -> VerifyPlaceGoal

这样做有几个原因。

原因一：任务分解依赖真实世界

如果一开始就把完整任务树固定下来，系统可能基于过期或尚未确认的对象信息生成很多无效步骤。

原因二：修复路径无法提前完全知道

路线是否被阻挡、哪个对象是可移动障碍物、哪个停车区域可用，通常只有在运行时结合当前快照才能确定。

原因三：避免过度承诺

系统可以先承诺高层目标，再根据现实逐步展开细节。这和一次性生成一份很长但未经验证的脚本不同。

原因四：让每次展开都有边界

分解器只能返回类型化的 GraphDelta。它不是把一段任意代码注入解释器，而是申请增加一组受约束的节点和边。

5.3 “编译”与“解释”的分工

编译阶段：
    检查输入格式
    检查选择器
    创建根节点
    建立初始任务定义

解释阶段：
    检查目标
    检查前置条件
    展开子树
    执行系统操作或物理动作
    验证后置条件
    处理失败和修复

所以这套系统不是“LLM 生成后就结束”，而是：

LLM 产出程序入口，内核运行这个程序，现实世界不断返回新的输入。

6. 意图层：自然语言如何变成 TaskProgram

6.1 一个自然语言任务

把红色杯子放到收纳区。

在系统里，最小的结构化表达可以近似写成：

{
  "program_id": "task-0001",
  "action": "place",
  "arguments": {
    "object_selector": {
      "entity_kind": "object",
      "relation": "first",
      "required_tags": ["red", "cup"],
      "reference": "robot",
      "frame": "world",
      "metric": "euclidean",
      "cardinality": "one",
      "tie_policy": "stable_id"
    },
    "destination_selector": {
      "entity_kind": "region",
      "relation": "first",
      "required_tags": ["storage"],
      "reference": "robot",
      "frame": "world",
      "metric": "euclidean",
      "cardinality": "one",
      "tie_policy": "stable_id"
    }
  }
}

当前核心参考实现中的 TaskProgram 主要支持 place 动作，并要求对象和目的地使用 SpatialSelector 表达。GeminiER2 适配层还会对外部 Harness 程序做规范化、翻译和兼容处理。

6.2 为什么不能只传两个字符串

简单写成：

{
  "object": "红色杯子",
  "destination": "收纳区"
}

会丢失很多重要信息：

- “红色杯子”是精确 ID 还是语义查询？
- 有多个候选时如何排序？
- “左边”“最近”相对于机器人还是相对于另一个物体？
- 选择结果是一件还是多件？
- 平局时是否稳定？
- 选择使用哪个坐标系？
- 这个选择是否能被复现？

SpatialSelector 把这些信息显式化。当前参考实现支持的关键字段包括：

| 字段 | 含义 |
| --- | --- |
| entity_kind | object、region 等实体类别 |
| relation | exact、first、nearest、leftmost、rightmost、farthest、corner |
| entity_id | 精确选择时使用的实体 ID |
| required_tags | 必须具有的语义标签 |
| region_id | 限定在某个区域内选择 |
| reference | 参考对象，默认可为机器人 |
| reference_entity_id | 以某个实体作为参考 |
| frame | 选择所在坐标系 |
| metric | 距离度量 |
| cardinality | 选择一个还是多个 |
| tie_policy | 平局时如何稳定决策 |
| corner | 选择区域角点时的角点名称 |

当前核心参考实现收紧了几个边界：

- cardinality 必须是 one；
- tie_policy 使用 stable_id；
- metric 使用 euclidean。

这些限制牺牲了一些灵活性，换来的是可预测性和容易测试。

6.3 LLM 在这里做什么

LLM 适合完成：

理解“红色杯子”
理解“收纳区”
理解“保持直立”
把隐含意图转换成选择器和约束
发现用户没有说清楚的地方
请求澄清

LLM 不应该完成：

直接给出机械臂关节电压
直接改写运行时节点状态
直接声称“已经放好”
把不可行的路径伪装成可行路径

这就是“模型做意图编译器，而不是做物理执行器”的边界。

----------------------------------------------------------------
7. 任务程序层：任务树为什么像运行时代码

7.1 TaskNodeSpec：静态程序定义

一个节点的静态定义近似如下：

TaskNodeSpec(
    node_id="program/task-0001",
    task_type="Place",
    operation_kind=OperationKind.DECOMPOSER,
    control_kind=ControlKind.SEQUENCE,
    origin=NodeOrigin.PROGRAM,
    parameters={
        "scope": "task-0001",
        "object_selector": ...,
        "destination_selector": ...,
        "repair_depth": 0,
    },
    preconditions=(),
    postconditions=(),
    max_attempts=1,
    max_repairs=0,
    execution_policy=ExecutionPolicy.SKIP_IF_GOAL_SATISFIED,
)

它回答的是：

这个节点是什么？
它属于哪一类操作？
它有哪些参数？
它成功前需要什么？
它成功后要满足什么？
它最多尝试几次？
它能否被修复？

7.2 TaskNodeRuntime：本次调用的运行状态

同一个节点在运行时还会有另一份状态：

TaskNodeRuntime(
    status=NodeStatus.RUNNING,
    phase="execute",
    attempts=1,
    repairs=0,
    expanded=True,
    output_artifacts=("transfer-plan-...",),
    last_diagnostic=None,
    started_at=...,
    finished_at=None,
    adapter_state={
        "active_request_id": "...",
    },
    active_obligations=(),
)

它回答的是：

这次执行到哪了？
已经试了几次？
是否展开过？
产出了哪些工件？
最近一次为什么失败？
有没有活跃的物理请求？

7.3 为什么必须分离 Spec 和 Runtime

如果把定义和运行状态混在一起，会产生几个问题：

1. 同一个任务定义无法复用  
   静态任务类型和本次执行进度被绑死。
2. 重试会覆盖历史  
   你看不到第一次尝试和第二次尝试的差别。
3. 审计困难  
   不容易判断“原计划是什么”和“运行后变成了什么”。
4. 并发或多会话更难处理  
   每次调用需要独立的运行态。
5. 恢复困难  
   重新加载时需要知道节点定义和节点进度分别是什么。

分离后可以把它理解为：

TaskNodeSpec    = 程序的定义
TaskNodeRuntime = 这次调用的实例状态

7.4 TaskEdge：控制流不是藏在代码里

当前边有两种：

child   普通子任务关系
repair  由失败触发的修复子任务关系

普通任务：

Place
  └── child -> PlanPick

修复任务：

PlanTransfer
  └── repair -> RouteBlockedRepair

把 repair 单独建成边，而不是把它藏在某个函数内部，有三个好处：

- 能看出原任务和修复任务的关系；
- 能统计任务真正经历了多少次修复；
- 能在回放时区分正常流程和异常流程。

7.5 GraphDelta：受约束的运行时增量代码

分解器和修复器不能直接写 Store，只能返回：

GraphDelta(
    nodes=(AddNode(...), ...),
    edges=(AddEdge(...), ...),
    root_id=None,
)

它类似“向运行时申请加载一段代码”，但内核会先检查：

- 节点是否属于允许的子树；
- 边是否指向已声明或合法存在的节点；
- repair 是否只有一条挂载边；
- 是否产生环；
- 所有节点是否可达；
- 是否越过当前任务边界；
- 是否试图替换根节点。

这意味着动态任务树不是任意自修改程序，而是：

被图结构不变量约束的有限运行时扩展。

7.6 ExecutionFrame：任务树的调用栈

内核维护持久化执行栈。每个栈帧记录：

ExecutionFrame(
    node_id="...",
    phase=FramePhase.EXECUTE,
    next_child_index=0,
    active_child_id=None,
    original_diagnostic=None,
    last_child_diagnostic=None,
)

当前阶段包括：

ENTER
GOAL_CHECK
PRECONDITIONS
EXECUTE
VERIFY
CHILDREN
REPAIR
RECONCILIATION

这和函数调用栈的关系很像：

根节点调用子节点
子节点未完成时暂停父节点
子节点成功后返回父节点
子节点失败时把诊断带回父节点
父节点决定重试、修复或失败

7.7 事件日志：运行过程不是黑盒

Store 还保存追加式事件日志。事件把以下对象串起来：

节点
运行状态
执行阶段
工件引用
物理请求
事务
世界快照引用
诊断
修复挂载

因此，在任务结束后，可以追问：

为什么执行了这个动作？
这个动作使用的是哪个计划？
这个计划基于哪个世界版本？
动作之后看到了什么？
为什么认为动作成功？
为什么触发修复？
修复之后重算了哪些计划？

----------------------------------------------------------------
8. 世界模型：运行时面对的“外部内存”

8.1 WorldSnapshot 不是任务树

任务树记录：

我要做什么
做到哪一步
哪一步失败

世界快照记录：

现实中现在有什么
每个实体在哪里
机器人当前姿态是什么
地图和坐标系版本是什么

两者必须分开：

TaskTreeStore  = 程序执行状态
WorldModel     = 现实观察状态
ArtifactStore  = 基于现实计算出的中间结果

如果把三者混成一个 JSON，系统会无法清楚区分：

- “任务想把杯子放到那里”；
- “杯子实际上已经在那里”；
- “规划器曾经认为杯子可以到那里”。

8.2 当前核心模型的结构

WorldSnapshot
├── revision
├── frame_graph_revision
├── grid
│   ├── width
│   ├── height
│   ├── resolution
│   ├── origin_x / origin_y
│   ├── static_occupied
│   └── revision
├── robot: RobotState
└── entities: EntityState[]

8.3 EntityState：物体、区域、障碍物都用实体表示

EntityState(
    entity_id="cup-red",
    kind="object",
    pose=Pose(...),
    radius=0.12,
    tags=frozenset({"red", "cup"}),
    properties={
        "movable": True,
        "nav_obstacle": False,
        "arm_obstacle": False,
    },
    version=3,
)

字段含义：

| 字段 | 含义 |
| --- | --- |
| entity_id | 稳定实体标识 |
| kind | 实体类别，例如 object、region |
| pose | 位置、朝向和坐标系 |
| radius | 参考几何尺寸 |
| tags | 语义标签，用于选择和分类 |
| properties | 领域属性，如是否可移动、是否是导航障碍 |
| version | 这个实体自身发生变化的版本 |

properties 的重要性在于：实体的“物理存在”和“任务语义”可以同时表达。

例如同一个实体可以是：

{
  "entity_id": "movable-crate",
  "kind": "object",
  "radius": 0.25,
  "tags": ["crate"],
  "properties": {
    "movable": true,
    "nav_obstacle": true,
    "arm_obstacle": true
  }
}

它同时具有：

- 是一个物体；
- 可以被移动；
- 会挡住底盘路线；
- 也可能挡住机械臂。

8.4 RobotState：机器人不是一个黑盒位置

RobotState(
    base_pose=Pose(...),
    joints=(0.2, -0.6),
    gripper_open=True,
    held_object_id=None,
    state_epoch=14,
)

字段含义：

| 字段 | 含义 |
| --- | --- |
| base_pose | 移动底盘在世界中的位置和朝向 |
| joints | 当前机械臂关节配置 |
| gripper_open | 夹爪是否打开 |
| held_object_id | 当前夹持的实体 |
| state_epoch | 机器人状态变化代数 |

state_epoch 很重要。因为一个抓取计划依赖机器人当时的关节状态。如果机器人已经移动过，原来的接近路径可能不再适用。

8.5 Observation：现实返回给系统的证据

物理命令之后，后端返回：

Observation(
    robot=RobotState(...),
    entities=(EntityState(...), ...),
    frame_graph_revision=...,
)

Observation 本身不是最终的世界版本。它被 WorldModel.ingest() 接收后，才产生新的：

world:0 -> world:1 -> world:2 -> ...

当前参考实现中：

- 每次 ingest 都推进 WorldSnapshot.revision；
- 如果实体的姿态、尺寸、标签或属性发生变化，就增加该实体的 version；
- 如果机器人姿态、关节、夹爪或持有物发生变化，就增加 state_epoch；
- 坐标系变化通过 frame_graph_revision 表达。

----------------------------------------------------------------
9. 规划工件：把“计算结果”变成可追踪的数据产品

9.1 为什么需要 Artifact

如果规划器只在函数内部返回一个临时变量：

path = planner.plan(...)

那么外部很难知道：

- 这条路径基于哪个世界状态；
- 使用了哪个机器人模型；
- 哪些障碍物被考虑了；
- 是否忽略了当前被抓住的物体；
- 机器人关节状态是否已经改变；
- 这条路径是否仍然新鲜；
- 哪个动作消费了它。

因此规划结果被建模成不可变工件：

BindingArtifact
NavigationPlan
PickPlan
TransferPlan

9.2 四类主要工件

BindingArtifact

记录语义选择最终绑定到了哪个实体：

“红色杯子” -> cup-red
“收纳区”   -> drop-zone

同时保留候选集合和选择依据。

NavigationPlan

记录：

- 起点；
- 终点；
- 路径点；
- 路径代价；
- 清障半径；
- 被明确忽略的实体集合。

PickPlan

记录：

- 要抓取的对象；
- 使用的导航计划；
- 底盘抓取站位；
- 抓取姿态；
- 机械臂接近路径；
- 抓取关节配置。

TransferPlan

记录：

- 要运输的对象；
- 目标区域；
- 运输导航计划；
- 目标站位；
- 放置姿态；
- 运输姿态；
- 到运输姿态的路径；
- 放置路径；
- 朝向容差。

9.3 工件元数据为什么比路径本身更重要

每个工件都带有类似下面的元数据：

ArtifactMetadata(
    snapshot_ref="world:7",
    dependency_versions=(
        ("arm", ...),
        ("entity:cup-red", 1),
        ("entity:drop-zone", 0),
        ("map", 3),
        ("frame_graph", 2),
        ("nav_occupancy:", ...),
    ),
    frame_graph_revision=2,
    robot_state_epoch=14,
    robot_model_version="reference-arm-v1",
    collision_model_version="reference-collision-v1",
    payload_transform_hash="cup-red:0.120000",
    assumptions=(...),
    random_seed=0,
)

这使工件可以回答：

我是在 world:7 上生成的
我依赖杯子版本 1
我依赖收纳区版本 0
我依赖当前地图和障碍物指纹
我假设机器人处于 state_epoch 14
我使用 reference-arm-v1
我使用 reference-collision-v1

9.4 新鲜度：计划不是永远有效

当前系统不会简单地把所有旧工件改成：

invalidated = true

而是根据工件声明的依赖版本和当前快照比较，推导它是否新鲜：

工件记录：
    entity:cup-red = 1
    map = 3
    robot = 14

当前快照：
    entity:cup-red = 2
    map = 3
    robot = 15

结论：
    工件过期

这样做的好处：

- 过期原因可解释；
- 不需要让一个可变标志成为唯一事实；
- 可以精确知道是哪一个依赖变了；
- 可以决定只重算受影响的部分。

9.5 工件依赖图

BindingArtifact
        │
        ▼
    PickPlan
        │
        ▼
  TransferPlan
        │
        ▼
 ActionRequest

如果重新生成了 PickPlan，依赖它的 TransferPlan 也必须重新生成，不能只更新一半。

工件存储采用：

不可变 artifact：
    永远保留，不原地修改

可变 scoped alias：
    “当前 pick_plan”指向最新版本

这类似于：

历史提交不可改
分支指针可以移动

9.6 算法为什么不是任务树节点

以下算法属于能力内部实现：

A*
IK
RRT
MPC

它们不应该变成任务树节点：

错误示例：
Place
  └── AStarIteration_001
      └── AStarIteration_002

正确方式是：

Place
  └── PlanTransfer
          └── 内部调用 A*
          └── 产出 NavigationPlan

任务树记录有业务意义的动作：

规划转移
执行抓取
确认已持有

而不是记录算法的每一轮内部计算。

这样可以保证：

- 换 A* 实现不改变任务语义；
- 换成 RRT 或 MPC 不需要改变任务树；
- 日志仍然围绕业务步骤，而不是充满数学迭代；
- 规划失败可以归属于 PlanTransfer，而不是一堆内部循环。

----------------------------------------------------------------
10. 任务内核：真正的“运行时解释器”

10.1 TaskTreeStore 是唯一权威状态

当前架构最重要的所有权规则是：

TaskTreeStore 拥有：
    TaskNodeSpec
    TaskNodeRuntime
    TaskEdge
    ExecutionFrame stack
    append-only event log

其他模块可以读取，但不能各自保存一份“差不多的运行时树”。

10.2 TaskTreeKernel 是唯一写入者

TaskTreeKernel 同时承担两种职责：

1. 唯一的节点生命周期解释器；
2. TaskTreeStore 的唯一写入者。

这意味着：

LLM            不能直接写 Store
Decomposer     只能返回 GraphDelta
RepairResolver 只能返回 RepairProposal
Inspector      只能读
Web Console    只能通过适配器读或提交任务

为什么要这样做？

如果多个模块都能改树：

分解器添加了一个节点
修复器同时删除了另一个节点
Web 控制台又把状态改成 succeeded

那么系统无法知道哪一个状态是真实权威。

单写入者模型把状态变化集中到一个地方，便于：

- 检查不变量；
- 做原子更新；
- 记录事件；
- 重放执行；
- 定位责任。

10.3 节点生命周期

一个典型节点大致按以下阶段推进：

ENTER
  ↓
GOAL_CHECK
  ↓
PRECONDITIONS
  ↓
EXECUTE 或展开 CHILDREN
  ↓
VERIFY
  ↓
SUCCEEDED

失败时可能进入：

诊断
  ├── 可重试：回到执行或目标检查
  ├── 需要重新规划：挂载 repair 子树
  ├── 物理结果不确定：进入 reconciliation
  └── 无法恢复：FAILED / BLOCKED

10.4 目标检查和前置条件不是一回事

当前节点有两种重要策略：

SKIP_IF_GOAL_SATISFIED
REQUIRE_EXECUTION

对某些幂等目标节点，如果进入时目标已经满足，可以直接成功：

VerifyPlaceGoal
    发现 object_at 已满足
    -> 成功

但结构节点或必须产生副作用的节点不能因为目标看起来满足就跳过整个结构流程。它们需要先展开或执行，再在后置阶段统一验证。

否则可能出现这种错误：

任务目标碰巧已经满足
    -> 复合节点直接跳过
    -> 任务树没有留下预期的结构和证据

10.5 当前执行是串行的

当前 ContinuousTaskSession 一次只接受一个正在运行的任务：

任务 1 完成
    ↓
任务 2 才能提交

这不是并行调度系统。即使未来要支持多任务并行，也需要额外设计：

- 资源仲裁；
- 物理互斥；
- 多树之间的世界一致性；
- 冲突检测；
- 取消和抢占；
- 多机器人协同。

当前的清晰边界是：

每个任务拥有独立的任务树
所有任务共享连续的物理世界
当前调度方式为串行

----------------------------------------------------------------
11. 物理边界：从“程序步骤”到真实副作用

11.1 三种节点角色

当前节点按操作职责区分：

| operation_kind | 作用 | 是否直接触碰机器人 |
| --- | --- | --- |
| decomposer | 把高层任务展开成子任务 | 否 |
| system | 读世界、做选择、规划、发布工件、验证 | 否 |
| physical | 消费工件并构造物理动作请求 | 不能绕过 Runtime |

物理技能不是机器人后端。它只负责把计划翻译成：

ActionRequest(
    request_id="...",
    action_name="NavigateHeld",
    commands=(...),
    resources=frozenset({"base"}),
    artifact_refs=("...", "..."),
    preconditions=(...),
)

11.2 ActionRequest 是一次受限系统调用

它包含：

| 字段 | 含义 |
| --- | --- |
| request_id | 幂等标识，避免同一请求重复派发 |
| action_name | 物理动作名称 |
| commands | 导航、机械臂路径、夹爪等规范化命令 |
| resources | 要占用的资源，如 base、arm、gripper |
| artifact_refs | 消费了哪些计划工件 |
| preconditions | 动作发送前需要满足的谓词 |

关键点：

PhysicalSkill 生成请求
HarnessRuntime 审查并执行请求
RobotBackend 执行具体命令

这样技能不能偷偷绕过：

- 工件新鲜度检查；
- 快照谓词保护；
- 资源租约；
- 事务；
- 取消机制；
- 观察回收；
- 结果对账。

11.3 唯一物理入口

物理路径是：

ActionRequest
    ↓
HarnessRuntime
    ├── 检查工件是否新鲜
    ├── 检查当前快照中的前置条件
    ├── 原子获取资源租约
    ├── 创建 checkpoint
    ├── 执行每条物理命令
    ├── 每条命令后采集 Observation
    ├── 提交、回滚或进入对账
    └── 返回 PhysicalActionOutcome

这条边界的设计动机是：

所有会产生现实副作用的请求，必须经过同一组安全、版本、事务和观察规则。

11.4 模拟器可以回滚，真实机器人通常不能

参考模拟器可以把内存状态恢复到 checkpoint：

checkpoint
    ↓
执行失败
    ↓
restore(checkpoint)

真实机器人通常不能把已经发生的物理运动真正撤销。因此生产后端应当：

supports_rollback = False
动作失败或结果不明
    ↓
重新观察现实
    ↓
reconciliation
    ↓
基于观察结果继续或重新规划

这体现了软件事务和物理事务的根本差别：

软件事务可以恢复内存
物理事务只能恢复“对现实的认识”

----------------------------------------------------------------
12. 观察和验证：系统如何知道自己没有自欺

12.1 “命令成功”不等于“目标成功”

至少要区分四件事：

规划器认为路径存在
命令已经发送
后端报告动作完成
传感器证据证明目标状态已经成立

例如夹爪命令返回成功，只说明：

夹爪控制接口接受并完成了闭合动作

它不自动证明：

杯子被夹住了
杯子没有滑落
杯子还在夹爪里

因此系统在物理动作之后必须生成 Observation，再由验证器检查：

object_held(cup-red)
object_released(cup-red)
object_at(cup-red, drop-zone)
base_near(target_pose)
joints_near(target_joints)

12.2 Verifier 的纯函数性质

核心验证器的设计约束是：

Verifier.evaluate(formula, snapshot)

它只读取：

- 谓词公式；
- 不可变 WorldSnapshot。

它不调用：

- 规划器；
- 物理技能；
- 控制器；
- 后端；
- 修复器。

这样“判断事实”和“改变事实”被分开了。

例如：

Verifier.evaluate(
    PredicateFormula(
        "object_at",
        {
            "object_id": "cup-red",
            "destination_id": "drop-zone",
        },
    ),
    snapshot,
)

结果包含：

satisfied: true / false
evidence:
    predicate
    snapshot_ref
    distance
    tolerance
    object_pose
    destination_pose

失败时不是返回一句“好像没放好”，而是返回带快照引用的证据。

12.3 OUTCOME_UNKNOWN 是一个独立状态

现实系统经常遇到：

动作已经发出
后端连接中断
无法确定机器人到底完成到哪一步

这不能简单等同于：

动作肯定失败

也不能等同于：

动作肯定成功

因此架构区分：

FAILED
OUTCOME_UNKNOWN
RECONCILIATION

系统需要先重新观察、对账，再决定是否允许继续提交动作。

13. 示例一：正常执行“把杯子放到收纳区”

下面用完整流程把前面的对象串起来。

13.1 初始世界

world:0

机器人：
    base = (0.20, 0.30, 0.00)
    joints = (0.20, -0.60)
    gripper = open
    holding = none

对象：
    cup-red    = (0.75, 0.40)
    drop-zone  = (1.25, 0.60)

约束：
    cup-red movable = true
    drop-zone acceptance_radius = 0.15

13.2 自然语言转成程序

用户：
    把红色杯子放到收纳区。

LLM / Planner Adapter：
    object_selector = kind=object, tags={red,cup}
    destination_selector = kind=region, tags={storage}

TaskProgram：
    action = place

13.3 编译初始根节点

编译器只创建根：

program/task-0001 : Place

此时还没有把完整的 16 个节点全部写入 Store。

13.4 根节点展开

运行时，Place 分解成：

Place
├── ResolveAndInspect
├── PlanPick
├── PlanTransfer
├── Pick
│   ├── NavigateToPickStance
│   ├── ExecuteGrasp
│   └── VerifyHeld
├── TransferHeld
│   ├── MoveToTransportPosture
│   ├── NavigateHeld
│   └── VerifyPlacementReady
├── Release
│   ├── ExecuteRelease
│   └── VerifyReleased
└── VerifyPlaceGoal

节点总数为 16，普通 child 边为 15，修复边为 0。

13.5 绑定阶段

ResolveAndInspect 读取 world:0：

object selector      -> cup-red
destination selector -> drop-zone

生成：

BindingArtifact
    object_id = cup-red
    destination_id = drop-zone
    source_snapshot = world:0
    dependency:
        entity:cup-red = 0
        entity:drop-zone = 0

13.6 规划抓取

PlanPick 消费绑定工件，调用机械臂和底盘规划能力：

输入：
    cup-red 的位置
    当前机器人关节
    地图
    碰撞模型

输出：
    PickPlan
    NavigationPlan

规划工件记录：

生成快照 = world:0
机器人 state_epoch = 0
机器人模型 = reference-arm-v1
碰撞模型 = reference-collision-v1

13.7 预先规划运输

PlanTransfer 在机器人还没有拿住杯子之前规划运输路线。

这样做的动机是：

先在空手状态发现路线不可行
    比
已经抓住杯子后才发现无法运输
    更容易修复

如果杯子会改变机器人通过空间，还要把杯子的载荷包络纳入路线检查。

13.8 执行抓取

NavigateToPickStance 生成：

ActionRequest
    action_name = NavigateToPickStance
    resources = {base}
    artifact_refs = {navigation_plan, pick_plan}

运行时检查：

工件是否新鲜？
当前底盘是否满足前置条件？
base 是否可租约？

执行后得到 Observation，世界推进：

world:0 -> world:1

然后 ExecuteGrasp 生成：

ArmPathCommand(...)
GripperCommand(close=True, object_id="cup-red")

执行后观察到：

gripper_open = false
held_object_id = cup-red

世界可能推进到：

world:2
robot.state_epoch = 1

VerifyHeld 读取新的世界快照，而不是相信技能返回的文字：

object_held(cup-red) = true

13.9 持物运输和释放

接下来大致是：

MoveToTransportPosture
    -> 观察
NavigateHeld
    -> 观察
VerifyPlacementReady
    -> 观察并确认持有、底盘位置
ExecuteRelease
    -> 观察
VerifyReleased
    -> 确认 held_object_id != cup-red
VerifyPlaceGoal
    -> 确认 cup-red 在 drop-zone 容差内

最终参考案例的统计为：

status: succeeded
节点数: 16
child 边: 15
repair 边: 0
事件数: 127
物理事务: 5
world:0 -> world:7

这些数字表达的不是“调用了 5 个 API”，而是：

5 次物理事务
每次事务后都有观察
世界版本经历了 7 次推进
任务树留下了完整的解释轨迹

14. 示例二：路线被箱子挡住时的递归修复

这是最能体现“运行时代码”特征的例子。

14.1 初始任务

用户：
    把红色杯子放到收纳区。

世界中多了一个障碍物：

movable-crate
    movable = true
    nav_obstacle = true
    arm_obstacle = true

14.2 规划失败

PlanTransfer 运行时发现路线不可行，返回：

{
  "code": "ROUTE_BLOCKED",
  "message": "Transfer route is blocked",
  "details": {
    "blocker_id": "movable-crate",
    "source_snapshot": "world:0",
    "retryable": true,
    "repairable": true
  }
}

此时任务不是马上终止，也不是让 A* 偷偷把箱子移开。

14.3 反事实证明

修复器先需要回答：

如果暂时忽略 movable-crate，
从当前起点到目标是否真的存在路线？

只有当反事实 A* 证明：

移除这个具体障碍物后路线恢复

并且同时满足：

障碍物确实存在
障碍物是 movable
存在合法停车区域
修复深度没有超限
当前夹爪没有占用一个不能放弃的载荷

才允许提出移动障碍物的修复。

14.4 修复提案不是直接执行

修复器返回：

RepairProposal(
    delta=GraphDelta(...),
    entry_node_id=".../repair-0/route-blocked",
    rationale=(
        "Relocate verified blocker movable-crate "
        "to parking region parking-zone"
    ),
    invalidates_artifacts=(),
)

其 GraphDelta 申请新增：

RouteBlockedRepair
    parent = 原失败的 PlanTransfer
    edge kind = repair

内核负责验证并挂载，修复器不能自行改树。

14.5 修复树

挂载后可以看到：

Place(cup-red -> drop-zone)
├── ResolveAndInspect
├── PlanPick
├── PlanTransfer
│   └── repair -> RouteBlockedRepair
│       └── Place(movable-crate -> parking-zone)
│           ├── ResolveAndInspect
│           ├── PlanPick
│           ├── PlanTransfer
│           ├── Pick
│           │   ├── NavigateToPickStance
│           │   ├── ExecuteGrasp
│           │   └── VerifyHeld
│           ├── TransferHeld
│           │   ├── MoveToTransportPosture
│           │   ├── NavigateHeld
│           │   └── VerifyPlacementReady
│           ├── Release
│           │   ├── ExecuteRelease
│           │   └── VerifyReleased
│           └── VerifyPlaceGoal
├── Retry PlanTransfer
├── Pick(cup-red)
├── TransferHeld(cup-red)
├── Release(cup-red)
└── VerifyPlaceGoal

这里不是简单地把失败节点改成成功，而是：

原任务保留
失败原因保留
修复动作显式出现
修复成功后重新规划
原目标继续执行

14.6 为什么移动障碍物必须成为任务节点

错误做法：

A* 发现箱子挡路
    -> 在规划器内部修改地图
    -> 假设箱子已经不在原处
    -> 输出一条新路线

这会产生一个隐藏副作用：

计划认为箱子被移走
现实中箱子仍然在原地
任务树没有记录谁移动了箱子

正确做法：

移动障碍物是一个真实动作
    -> 必须有任务节点
    -> 必须生成动作请求
    -> 必须有观察结果
    -> 必须更新 WorldSnapshot
    -> 必须重新规划依赖工件

这就是“物理副作用显式化”原则。

14.7 修复完成后的重新规划

障碍物被放到停车区后：

world:0 -> ... -> world:7

原来的路线工件不能直接继续使用，因为：

障碍物位置变了
地图占用指纹变了
原计划依赖的世界版本已经过期

系统需要：

重新检查 BindingArtifact
刷新 PickPlan（必要时）
刷新 TransferPlan
重新验证路线
重试原来的目标节点

最终参考案例统计为：

status: succeeded
节点数: 34
总边数: 33
repair 边: 1
事件数: 275
物理事务: 10
world:0 -> world:14

这说明系统完成的不是：

失败 -> 假装成功

而是：

失败
-> 诊断
-> 证明修复条件
-> 挂载修复程序
-> 执行修复
-> 获取新观察
-> 重新计算
-> 重试原程序
-> 验证最终目标

14.8 修复任务也可能失败

例如停车区域也被挡住：

Place(movable-crate -> parking-zone)
    -> PlanTransfer
        -> ROUTE_BLOCKED

系统理论上可以继续递归修复，但必须有边界：

- 修复深度限制；
- 节点尝试次数限制；
- 最大对账次数；
- 资源占用限制；
- 不能抓取当前已经持有的对象以外的障碍物；
- 没有合法停车区时必须停止；
- 无法收敛时进入 BLOCKED 或人工介入。

递归不是无限自我调用，而是：

在明确的资源、深度和证据约束内，让修复任务复用同一套任务语义。

假设连续执行两条指令：

任务 0002：把红杯子放到收纳区

16. 这套系统到底是哪一种“程序”

为了避免概念混乱，可以把可能的说法逐一判断。

| 说法 | 是否准确 | 解释 |
| --- | --- | --- |
| 自然语言直接变成电机代码 | 否 | 中间还有任务、规划、请求和运行时边界 |
| LLM 生成 Python 控制脚本 | 否 | 当前 LLM 只提交受约束的程序意图 |
| 自然语言是高层源语言 | 是 | 它表达目标、约束和偏好 |
| TaskProgram 是中间表示 | 是 | 它把意图变成类型化结构 |
| 任务树是可执行程序 | 基本是 | 它有控制流、状态、生命周期和后置条件 |
| 任务树是通用编程语言 | 否 | 节点类型和能力范围是领域受限的 |
| 任务树会自修改 | 受限地是 | 只能通过经过校验的 GraphDelta 增量扩展 |
| 系统是反应式程序 | 是 | 每次动作后根据新观察决定下一步 |
| 系统是完全自主的机器人操作系统 | 还不是 | 当前是参考架构和受限运行时，生产能力仍需补齐 |
| 系统是传统工作流 | 不完全是 | 它还包含世界状态、连续观察、规划和物理修复 |

最准确的命名可以是：

受约束的自然语言任务编译器 + 机器人任务虚拟机 + 物理世界观察闭环。

或者更简洁：

自然语言驱动的机器人领域专用运行时。

17. 高层设计原则：每条原则解决什么问题

17.1 单一所有权

TaskTreeStore 是唯一权威树状态
TaskTreeKernel 是唯一写入者

解决的问题：

- 多模块同时修改导致冲突；
- 状态分叉；
- 无法判断谁写入了错误状态；
- 事件日志和真实状态不一致。

代价：

- 所有修改都要经过 Kernel；
- 需要设计明确的 mutation API；
- 某些看似简单的局部操作会多一层协议。

17.2 最小权限

不同角色拿到不同上下文：

DecompositionContext
    几乎没有服务能力

SystemOperationContext
    可以读世界、选择、规划、发布工件、验证

SkillContext
    只能读取工件和请求上下文

RepairContext
    可以读世界和工件，但不能改树

解决的问题：

- 让“不能做什么”由接口保证；
- 降低误用和越权；
- 让代码审查变得可操作；
- 避免一个模块逐渐变成“万能对象”。

17.3 计划与动作分离

Planner -> Artifact
Skill   -> ActionRequest
Runtime -> physical execution

解决的问题：

- 规划失败和动作失败混淆；
- 同一个计划被多个动作隐式消费；
- 计划过期时无法拦截；
- 物理动作绕过安全门禁。

17.4 观察优先于声明

动作返回成功 != 目标已经成立

解决的问题：

- 把 API 返回值误当成现实事实；
- 夹持丢失却继续运输；
- 物体没有到位却标记任务完成；
- 连接中断后错误重试。

17.5 不可变证据

WorldSnapshot 不可变
Artifact 不可变
事件追加而不是覆盖

解决的问题：

- 历史状态被悄悄修改；
- 无法回放；
- 无法比较新旧计划；
- 无法解释一次决策依赖的输入。

17.6 物理副作用必须显式进入任务树

移动障碍物
拿起物体
放下物体
恢复姿态

都必须成为可观察的任务步骤。

解决的问题：

- 规划器隐藏真实动作；
- 任务树与现实脱节；
- 恢复时不知道现场已经被改变；
- 审计记录缺少关键副作用。

17.7 算法是能力，不是业务步骤

A*、IK、RRT、MPC

留在能力内部。

解决的问题：

- 任务树被实现细节污染；
- 更换算法需要重写任务语义；
- 日志失去业务可读性；
- 算法迭代被误认为物理动作。

17.8 失败是数据，修复是程序

Diagnostic
    -> RepairProposal
    -> GraphDelta
    -> repair subtree

解决的问题：

- 所有失败都只能返回字符串；
- 恢复逻辑散落在异常处理代码里；
- 失败后只能从头重跑；
- 无法区分可修复和不可修复。

17.9 任务树和物理世界分离

一棵树 = 一个目标的执行历史
一个世界 = 连续的现实现场

解决的问题：

- 多条指令的任务状态混淆；
- 新任务错误重置场景；
- 第二条指令无法看到第一条指令造成的物理变化。

18. 安全与正确性分析

18.1 威胁一：LLM 生成错误意图

可能出现：

把区域当成物体
把两个实体绑定成同一个对象
生成未知量词
忽略用户约束
引用不存在的实体

应对机制：

- TaskProgram 类型校验；
- SpatialSelector 字段校验；
- 候选集合和稳定平局策略；
- 编译器规范化；
- 对歧义、未知字段和冲突值 fail closed。

18.2 威胁二：计划过期

可能出现：

规划时箱子在 A
执行时箱子已经移动到 B

应对机制：

- 快照引用；
- 实体版本；
- 地图版本；
- 障碍物占用指纹；
- 机器人状态代数；
- 机器人模型和碰撞模型版本；
- 执行前 freshness 检查；
- 过期后重新规划。

18.3 威胁三：重复发送物理动作

可能出现：

网络超时
上层以为没有发送成功
再次发送同一个抓取请求

应对机制：

- 稳定 request_id；
- Gateway 对同一请求只派发一次；
- 后续调用等待第一次结果；
- 物理结果不明时先进入 reconciliation。

18.4 威胁四：隐藏物理副作用

可能出现：

规划器为了找到路线，直接修改障碍物集合

应对机制：

- 规划器只能发布工件；
- 移动障碍物必须有任务节点；
- 物理动作只能通过 HarnessRuntime；
- 每个动作后都必须观察；
- 世界变化由 WorldModel 接收。

18.5 威胁五：错误的完成判断

可能出现：

夹爪闭合 -> 系统直接认为抓取成功
后端返回 done -> 系统直接认为物体已到位

应对机制：

- VerifyHeld；
- VerifyReleased；
- VerifyPlaceGoal；
- 基于不可变快照的证据；
- OUTCOME_UNKNOWN 与 FAILED 分离。

18.6 威胁六：修复无限循环

可能出现：

路线阻塞
    -> 移障
    -> 移障任务又阻塞
    -> 再移另一个障碍
    -> 无限递归

应对机制：

- max_repairs；
- repair_depth；
- max_node_attempts；
- max_reconciliations；
- 资源和持物状态检查；
- 无法收敛时 BLOCKED 或人工介入。

18.7 为什么安全不能只写进提示词

提示词可以告诉模型：

不要做危险动作

但它不能可靠地成为：

- 唯一权限系统；
- 事务边界；
- 版本检查器；
- 物理设备网关；
- 事实验证器。

真正的安全约束必须落在代码边界：

谁能写 Store
谁能拿 Backend
谁能发布 Artifact
谁能生成 ActionRequest
谁能验证现实
谁能挂载 repair

----------------------------------------------------------------
19. 当前架构的边界：哪些地方不能过度解读

19.1 当前核心 Store 是内存实现

当前 TaskTreeStore 的权威状态在进程内存中。JSON 导出适合：

- 检查；
- 调试；
- 回放输入；
- 生成报告。

但它还不是完整的崩溃恢复协议。生产实现需要在同一持久化事务边界中保存：

树定义
运行态
边
执行栈
事件
别名
工件
事务记录

19.2 当前机器人是参考模拟器

核心参考机器人是平面双连杆模型，并不等于真实工业机械臂的完整动力学和碰撞模型。

生产接入仍需补齐：

- 完整的末端执行器和载荷变换；
- 真实关节限制；
- 真实碰撞几何；
- 控制周期内的连续碰撞监测；
- 接触策略；
- 传感器误差模型；
- 安全停机和急停流程。

19.3 当前 Web 控制台是本地单操作员适配器

当前控制台主要用于本地操作和观察，没有完整认证体系。不能把它直接当作生产多用户控制面。

19.4 当前调度是串行

这套架构目前展示的是：

一个任务树 + 一个连续物理世界 + 串行任务会话

它还没有解决多任务并行和多机器人资源调度的全部问题。

19.5 自然语言理解仍可能含糊

类型化 TaskProgram 能约束结构，但不能自动消除所有语义歧义。

例如：

把杯子放到那里

如果“杯子”有多个候选，系统仍然需要：

- 请求澄清；
- 使用明确的选择策略；
- 或把候选集合交给人确认。

这属于意图层问题，不是任务内核单独能够解决的问题。

20. 一个更形式化的理解

可以把整个运行时状态抽象成：

S_t = (T_t, W_t, A_t, X_t, E_t)

其中：

| 符号 | 含义 |
| --- | --- |
| T_t | 当前任务树，包括 Spec、Runtime 和 Edge |
| W_t | 当前世界快照 |
| A_t | 当前可用的不可变工件及别名 |
| X_t | 当前执行栈 |
| E_t | 追加式事件日志 |

一个内核 tick 可以写成：

(T_t, W_t, A_t, X_t, E_t)
    --tick-->
(T_{t+1}, W_t, A_{t+1}, X_{t+1}, E_{t+1})

如果 tick 产生物理动作：

ActionRequest_t + W_t
    -> RobotBackend
    -> Observation_{t+1}
    -> W_{t+1}

如果发生失败：

Diagnostic_t + W_t
    -> RepairProposal / Reconciliation
    -> GraphDelta
    -> T_{t+1}

自然语言到程序的过程可以写成：

NL
    --interpret / normalize-->
TaskProgram
    --compile-->
TaskNodeSpec root
    --runtime expand-->
TaskGraph
    --interpret with W_t-->
ActionRequest sequence

这套系统的关键不是某个单独函数，而是让这些状态转换显式存在，并且每次转换都能被检查。

21. 如何阅读一次实际运行记录

学习或调试一次任务时，可以按下面顺序看。

第一步：看输入程序

先看：

TaskProgram.action
TaskProgram.arguments
object_selector
destination_selector

问自己：

用户想做什么？
对象如何被选择？
目标如何被选择？
有没有歧义？

第二步：看根节点和静态定义

看 TaskNodeSpec：

task_type
operation_kind
control_kind
origin
parameters
max_attempts
max_repairs
execution_policy

问：

这个节点是分解器、系统操作还是物理动作？
它是叶子还是复合节点？
它的目标和前置条件是什么？

第三步：看运行态

看 TaskNodeRuntime：

status
phase
attempts
repairs
expanded
output_artifacts
last_diagnostic
adapter_state

问：

它现在卡在哪个阶段？
是没有开始，还是已经发出请求？
失败之前尝试了几次？

第四步：看执行栈

栈顶通常是当前最具体的活动节点。

例如：

Place / CHILDREN
TransferHeld / CHILDREN
NavigateHeld / EXECUTE

可以理解成：

当前正在 Place 里面的 TransferHeld 里面执行 NavigateHeld

第五步：看工件

检查动作使用的工件：

artifact_id
kind
snapshot_ref
dependency_versions
robot_state_epoch
model versions
payload_transform_hash

问：

它基于哪个世界？
为什么现在仍然有效？
哪个依赖变化会让它过期？

第六步：看物理请求和观察

把下面两件事对照起来：

ActionRequest：
    系统想让机器人做什么

Observation：
    机器人做完后现实变成什么

不要只看请求，不看观察。

第七步：看验证证据

看：

Verifier formula
snapshot_ref
measured value
tolerance

问：

成功是由什么证据证明的？
如果没有证据，是否应该是 OUTCOME_UNKNOWN？

第八步：看诊断和修复边

如果失败，检查：

Diagnostic.code
Diagnostic.details
retryable
repairable
repair edge
repair subtree

这样才能看出系统是：

单纯重试
重新规划
执行物理修复
进入对账
还是最终阻塞

22. 对这套架构的总体评价

22.1 它解决了什么核心问题

它把传统 Agent 中容易隐含的几件事拆开了：

意图理解
任务分解
现实建模
规划
物理执行
观察
验证
失败处理

并且为每件事规定了边界。

最有价值的转变是：

从“模型不断调用工具”
变成
“模型提交任务程序，运行时推进任务程序”

22.2 它带来的能力

可解释

可以从树、边、事件、工件和快照解释每一步。

可恢复

失败可以进入明确的 retry、repair 或 reconciliation。

可测试

可以测试：

- GraphDelta 是否越界；
- 图是否有环；
- 工件是否过期；
- 物理请求是否满足前置条件；
- 观察后是否正确推进世界版本；
- 修复树是否正确挂载。

可替换

可以在不改变任务语义的情况下替换：

- A*；
- IK；
- RRT；
- MPC；
- 机器人后端；
- Harness 适配器。

可观测

任务树和物理世界分别可视化，连续任务也可以保留独立历史。

22.3 它付出的代价

这种架构不是没有代价：

- 类型和契约更多；
- 组件间接口更严格；
- 物理动作前后的检查增加延迟；
- 任务树和事件日志会产生存储开销；
- 生产持久化和恢复实现更复杂；
- 多任务并行需要额外调度系统；
- 现实世界不确定性仍然无法被完全消除。

但这些代价换来的不是“代码更漂亮”，而是：

错误可以被定位
失败可以被解释
动作可以被拦截
计划可以被判定为过期
现实可以重新对账

对于会产生真实物理副作用的系统，这是更重要的价值。

----------------------------------------------------------------
23. 仍然值得继续思考的方向

23.1 从结构化程序到更完整的任务语言

未来可以扩展：

- 多对象任务；
- for_each；
- 条件分支；
- 并行分支；
- 超时；
- 人工确认；
- 资源预算；
- 风险等级；
- 时间约束；
- 任务取消和抢占。

但扩展时仍应保持：

自然语言 -> 类型化 IR -> 内核解释

而不是重新回到任意代码生成。

23.2 把世界不确定性正式建模

当前核心参考模型主要是确定性的实体状态。生产系统还需要考虑：

- 感知置信度；
- 多假设实体绑定；
- 物体可能被遮挡；
- 位置估计误差；
- 接触状态不确定；
- 传感器延迟；
- 观察之间的时间窗口。

未来可以把：

WorldSnapshot

扩展成带不确定性和证据来源的世界信念状态，但必须避免让概率字段替代真实验证。

23.3 让持久化真正成为恢复协议

生产版需要保证：

树状态
执行栈
事件
工件
别名
物理事务

在一致的存储边界中落盘，并考虑：

- 进程崩溃；
- 网络重连；
- 后端重启；
- 请求重复提交；
- 观察延迟到达；
- 旧版本事件回放。

23.4 评估指标不能只看成功率

更完整的指标包括：

最终目标成功率
有证据的成功率
修复收敛率
人工介入率
过期计划拦截率
重复物理请求率
OUTCOME_UNKNOWN 占比
平均修复深度
平均重新规划范围
事件回放完整率
安全策略拦截次数

一个任务“最终成功”并不代表系统过程优秀。它可能是：

反复撞墙后偶然成功

也可能是：

一次正确规划，零隐藏副作用，证据完整

这两种成功应该被区分。

23.5 何时需要人工确认

不是所有任务都应该自动修复。以下情况可能需要人工确认：

- 目标绑定有多个同等候选；
- 修复动作会移动用户指定以外的物体；
- 物体价值或风险较高；
- 物理结果不明；
- 递归修复超过阈值；
- 需要进入可能伤害设备或环境的区域；
- 任务约束互相冲突。

人工确认也可以作为一种正式任务节点，而不是外部偷偷打断程序。

24. 最终结论

这套系统可以被看成四层转换：

自然语言
    -> 意图程序
意图程序
    -> 任务递归树
任务递归树
    -> 受约束的物理动作
物理动作
    -> 观察驱动的世界状态和下一步决策

所以它的本质不是：

“让大模型直接操纵机器人。”

而是：

让大模型把人的自然语言目标编译成一种机器人领域程序，再由一个拥有明确状态、权限、证据和恢复机制的运行时系统执行这份程序。

这个系统最值得记住的五句话是：

1. 自然语言表达意图，不直接表达电机控制。
2. 任务树是动态的领域程序，不是普通的待办清单。
3. 世界快照是现实证据，不是任务树的附属字段。
4. 工件把规划结果变成带版本和依赖的中间值。
5. 失败不是一句报错，而是可以驱动递归修复的程序输入。

如果要用一句最完整的话给这套架构下定义，可以说：

Task Recursive Tree Agent 是一个以自然语言为高层入口、以类型化任务树为中间程序、以 Kernel 为解释器、以 Artifact 为计划数据、以 HarnessRuntime 为物理系统调用边界、以 Observation 和 Verifier 为现实反馈闭环的机器人运行时架构。

第二部分：逐概念拆解课

这一部分故意从最基础的概念开始讲。假设读者知道机器人、软件和
大模型这几个词，但不知道它们在这套架构里如何拼在一起。

阅读时不要试图一次记住所有类名。先建立一个问题顺序：

人想让机器人做什么？
    ↓
系统把目标写成了什么数据？
    ↓
运行时现在保存了什么状态？
    ↓
系统依据哪个世界快照做决定？
    ↓
哪个模块真正产生了物理副作用？
    ↓
动作之后用什么证据判断结果？
    ↓
失败后是谁提出修复，谁批准修复，谁执行修复？

只要这七个问题能顺着回答，整套系统就不会再显得神秘。

25. 先把五个最基础的词讲清楚

25.1 什么是“数据”

数据就是系统保存或传递的描述。

例子：

杯子的名字是 cup-red
杯子的坐标是 (0.75, 0.40)
机器人夹爪现在是打开的
路线有 12 个路径点

数据本身不会自动做任何事情。

{"held_object_id": "cup-red"}

只是一个描述。它不会真的让夹爪抓住杯子。

25.2 什么是“状态”

状态是“在某个时刻，系统认为世界或程序是什么样”。

例如机器人有两个不同的状态：

物理世界状态：
    杯子在桌子上
    夹爪打开
    底盘位于 x=0.2, y=0.3

任务程序状态：
    Place 节点正在执行
    PlanPick 已经完成
    ExecuteGrasp 尚未验证

这两个状态不是同一个东西。

世界状态回答：现实是什么样？
程序状态回答：程序做到哪了？

如果只保存程序状态，不保存世界状态，系统会出现：

程序认为已经抓住杯子
现实中杯子其实掉在地上

如果只保存世界状态，不保存程序状态，系统会出现：

系统知道杯子在哪里
但不知道下一步要做什么

所以这套系统至少需要把二者分开保存。

25.3 什么是“动作”

动作是会改变世界的操作。

底盘沿路线移动
机械臂改变关节角
夹爪闭合
夹爪打开
移动一个箱子

动作有一个非常重要的特征：

动作不是“描述”，而是会产生副作用。

副作用就是“动作对外部世界造成的改变”。

读取杯子坐标：通常没有物理副作用
计算一条路线：通常没有物理副作用
让底盘移动：有物理副作用
让夹爪闭合：有物理副作用

架构要特别防止把有副作用的事情伪装成没有副作用的数据计算。

25.4 什么是“程序”

程序不一定非要写成 Python。只要它具备以下几类内容，就有程序的特征：

目标：
    要得到什么结果？

步骤：
    先做什么，后做什么？

状态：
    当前做到哪一步？

输入：
    依赖什么外部信息？

输出：
    产生什么结果？

条件：
    什么情况下可以继续？

异常：
    失败后怎么办？

任务递归树具备这些内容，所以它可以被称为“领域程序”。

25.5 什么是“运行时”

运行时不是一句“程序正在跑”这么简单。它至少包括：

解释规则：
    一个节点进入后先做什么？

内存：
    当前节点状态放在哪里？

调用栈：
    当前嵌套到哪一层？

输入环境：
    当前世界状态是什么？

副作用边界：
    谁有资格调用设备？

结果处理：
    动作完成后如何判断成功？

错误处理：
    失败后重试、修复还是终止？

TaskTreeKernel、TaskTreeStore、WorldModel、ArtifactStore 和
HarnessRuntime 合在一起，才构成完整的机器人任务运行时。

26. Agent、脚本、工作流和运行时程序的区别

26.1 普通脚本

第一行：移动到 A
第二行：抓取
第三行：移动到 B
第四行：释放

脚本通常假设环境已经知道，并且流程大致固定。

26.2 工作流

工作流比脚本更明确地表达：

步骤 1 完成后才能进入步骤 2
失败后走备用分支
某个审批通过后才能继续

26.3 Agent

Agent 通常还能根据输入和环境决定：

下一步做什么
调用哪个能力
遇到失败如何换方案

但是，如果 Agent 只是不断生成文字并调用工具，它的中间状态往往藏在：

提示词
对话历史
临时变量
模型内部的隐式推理

这会让过程难以审计。

26.4 这套系统的组合

这套架构把四者组合起来：

自然语言提供目标
Agent 提供理解和高层分解
任务树提供显式程序结构
运行时提供确定的执行和恢复规则

所以它不是“没有 Agent 的工作流”，也不是“把工作流交给模型随便决定”。

更准确地说：

Agent 负责提出和解释程序，运行时负责把程序变成受控行为。

27. 编译器类比：为什么这个类比有用

27.1 编译器做什么

编译器把人更容易写的形式，转换成机器更容易执行的形式。

源代码：
    x = 1 + 2

中间表示：
    load 1
    load 2
    add
    store x

机器人任务也存在类似转换：

自然语言：
    把红杯子放到收纳区

结构化意图：
    place(object_selector, destination_selector)

任务程序：
    resolve -> plan -> pick -> transfer -> release -> verify

物理请求：
    具体路线、关节路径、夹爪命令

27.2 为什么不能跳过中间表示

如果自然语言直接变成低层动作，中间缺少：

类型检查
对象绑定
前置条件
资源要求
证据引用
版本依赖
失败处理

这相当于让编译器把一句模糊的英文直接变成机器码，而且不允许检查变量、
内存和权限。

27.3 TaskProgram 是什么类型的中间表示

TaskProgram 不是最终执行图。它更像一个很小的抽象语法树：

动作名称：
    place

参数：
    object_selector
    destination_selector

它的作用是把输入从“人话”变成“结构化意图”。

27.4 TaskNodeSpec 是什么

编译器把 TaskProgram 编译成根节点 TaskNodeSpec。

此时的根节点像一条高层指令：

Place

它还没有包含每一次具体抓取的路径点。因为路径点要依赖当时的世界状态。

27.5 任务树为什么不是普通 AST

普通 AST 通常描述一段静态程序。任务树还需要描述：

当前执行状态
现实反馈
物理副作用
动态修复

所以它更接近：

AST
    + 状态机
    + 调用栈
    + 事件日志
    + 现实世界反馈

28. TaskProgram：从一句话变成一个小对象

28.1 人话定义

TaskProgram 就是：

“用户想做哪类任务，以及这个任务的结构化参数是什么。”

28.2 当前核心字段

TaskProgram(
    program_id="task-0001",
    action="place",
    arguments={
        "object_selector": ...,
        "destination_selector": ...,
    },
)

逐项解释：

program_id

任务的身份证。

task-0001

它不是机器人对象的 ID，也不是节点 ID。它标识的是“一次用户提交的任务程序”。

action

要执行的高层动作类型。

当前核心实现要求：

action == "place"

这意味着参考实现目前主要演示“把一个对象放到一个目标区域”。

arguments

任务参数。当前要求至少有：

object_selector
destination_selector

注意这里保存的不是已经解析出的实体对象，而是“如何找到对象”的规则。

28.3 为什么参数里保存选择器，而不是直接保存对象

如果直接保存：

object_id = cup-red

系统失去了对下面这句话的记录：

为什么选择了 cup-red？

而保存选择器可以记录：

用户说的是“红色杯子”
选择器要求 kind=object
选择器要求 tags={red,cup}
如果多个候选，使用 stable_id 平局策略

这让“理解”和“绑定”分成了两步。

28.4 TaskProgram 的边界

它可以表达：

要放置什么对象
放到什么目标

它不应该直接表达：

每个电机的电流
控制器周期
传感器驱动细节
底层通信包

这些信息属于后面的能力和物理运行时。

29. SpatialSelector：系统怎样理解“那个东西”

29.1 人话定义

SpatialSelector 是一个“找东西的规则”。

它不是对象本身，而是一份查询条件。

找一个 kind=object、带 red 和 cup 标签的实体

29.2 从“找红杯子”逐项拆开

SpatialSelector(
    entity_kind="object",
    relation=SelectionRelation.FIRST,
    required_tags=frozenset({"red", "cup"}),
    reference="robot",
    frame="world",
    metric="euclidean",
    cardinality="one",
    tie_policy="stable_id",
)

entity_kind

先按大类过滤。

object = 可被操作的物体
region = 区域或目标位置

如果目标是 region，就不应该绑定到一个普通杯子。

relation

规定候选之间怎样选。

当前可以有：

exact
first
leftmost
rightmost
nearest
farthest
corner

例如：

nearest:
    选离参考点最近的候选

leftmost:
    选 x 坐标最小的候选

corner:
    选最接近目标区域某个角的候选

entity_id

精确选择时使用。

SpatialSelector.exact("cup-red", "object")

它表达的是：

不要猜，必须是 ID 为 cup-red 的实体

required_tags

语义标签集合。

{red, cup}

表示候选必须同时拥有这两个标签。

region_id

限制候选必须位于某个区域内。

在桌面区域内，选择最近的红色杯子

这比只说“最近的红色杯子”更精确。

reference

距离或空间关系相对于谁计算。

robot
origin
另一个指定实体

“最近”不是绝对概念，必须有参考点。

frame

坐标系。

world
robot_base
camera

如果不说明坐标系，同一个 (x, y) 可能代表完全不同的位置。

当前参考选择器主要按世界坐标使用，但字段被保留下来，是为了让语义不被隐藏。

metric

距离怎么算。

当前参考实现使用欧氏距离：

distance = sqrt((x1-x2)^2 + (y1-y2)^2)

未来也可能有：

曼哈顿距离
路径代价
时间代价
风险加权距离

cardinality

要选几个。

当前参考实现只接受：

one

这是一种故意收紧的约束，避免一个本来只支持单物体的动作收到一组对象。

tie_policy

如果两个候选完全一样，怎么办？

当前使用：

stable_id

也就是按稳定 ID 排序，保证同样输入下结果可重复。

29.3 选择过程的完整例子

世界中有：

cup-blue   tags={cup,blue}  position=(0.5,0.4)
cup-red-1  tags={cup,red}   position=(0.8,0.4)
cup-red-2  tags={cup,red}   position=(0.9,0.4)

选择器：

kind=object
required_tags={cup,red}
relation=nearest
reference=robot

选择过程：

第一步：按 kind 过滤
    保留三个 object

第二步：按 tags 过滤
    删除 cup-blue
    保留 cup-red-1、cup-red-2

第三步：计算到机器人的距离
    cup-red-1 更近

第四步：如果距离相同
    按 stable_id 选

输出：
    selected = cup-red-1
    candidates = [cup-red-1, cup-red-2]
    rationale = 选择规则说明

29.4 选择器不能做什么

选择器只负责“找谁”，不能负责：

怎么走过去
用哪个抓取姿态
是否需要移动障碍物
机械臂如何避障

如果选择器开始调用 A* 或机器人控制，职责就混乱了。

30. BindingArtifact：把“我认为那个对象是谁”固定下来

30.1 为什么需要绑定结果

选择器是规则，绑定结果是这次执行的事实：

object_selector -> cup-red
destination_selector -> drop-zone

30.2 绑定工件包含什么

BindingArtifact(
    artifact_id="binding-...",
    metadata=...,
    object_id="cup-red",
    destination_id="drop-zone",
    object_candidates=("cup-red", "cup-red-2"),
    destination_candidates=("drop-zone",),
    grounding_evidence=(
        "nearest in frame=world, metric=euclidean, tie=stable_id",
        "first in frame=world, metric=euclidean, tie=stable_id",
    ),
)

逐项理解：

object_id：
    最终选中的对象

destination_id：
    最终选中的目标

object_candidates：
    当时所有符合条件的对象

destination_candidates：
    当时所有符合条件的目标

grounding_evidence：
    为什么选它的文字化依据

30.3 绑定也可能过期

如果对象消失、对象 ID 复用、目标区域版本改变，绑定工件依赖可能失效。

所以绑定不是永远正确，而是：

在某个世界快照下做出的选择结果

31. TaskNodeSpec：一个任务节点的“说明书”

31.1 节点不是一句名字

下面两个节点名字虽然不同，但如果没有结构化字段，内核仍不知道如何处理：

PlanPick
ExecuteGrasp

真正重要的是节点的属性：

它是系统操作还是物理操作？
它是叶子还是复合节点？
它来自用户程序还是修复？
它依赖哪些参数？
成功前需要满足什么？
成功后需要满足什么？

31.2 字段逐项解释

TaskNodeSpec(
    node_id="...",
    task_type="ExecuteGrasp",
    operation_kind=OperationKind.PHYSICAL,
    control_kind=ControlKind.LEAF,
    origin=NodeOrigin.DECOMPOSER,
    parameters={"scope": "task-0001"},
    preconditions=(...),
    postconditions=(...),
    max_attempts=2,
    max_repairs=1,
    execution_policy=ExecutionPolicy.REQUIRE_EXECUTION,
)

node_id

节点的唯一 ID。

它需要稳定到足以支持：

事件引用
执行栈引用
动作请求 ID
父子边
故障定位

task_type

业务语义名称。

PlanPick
ExecuteGrasp
VerifyHeld

这不是算法名称。A* 不应该成为 task_type。

operation_kind

告诉内核应该把节点交给哪类处理器：

decomposer：
    展开出子节点

system：
    执行选择、规划、验证等非物理操作

physical：
    生成并执行物理请求

control_kind

告诉内核节点的控制结构：

leaf：
    没有业务子节点，执行一个操作

sequence：
    按顺序完成所有子节点

selector：
    在候选分支中选择可行分支

当前 Place 参考流程主要使用 sequence。

origin

节点从哪里来：

program：
    用户程序直接产生

compiler：
    编译器产生

decomposer：
    运行时分解产生

repair：
    故障修复产生

这个字段是理解“任务是怎么长出来的”的关键。

parameters

节点自己的参数。

例如：

scope = task-0001
object_selector = ...
destination_selector = ...
repair_depth = 0

参数不是全局变量。每个节点应该尽量只依赖自己声明的参数和契约。

preconditions

执行前必须为真的条件。

例如：

机器人已经在抓取站位
夹爪没有占用其他物体
对象仍然存在
计划仍然新鲜

postconditions

执行后必须为真的条件。

例如：

ExecuteGrasp:
    object_held(cup-red)

ExecuteRelease:
    object_released(cup-red)

Place:
    object_at(cup-red, drop-zone)

max_attempts

节点最多尝试多少次。

它不是“失败就无限重来”的许可。

max_repairs

该节点最多允许挂载多少次 repair。

execution_policy

决定目标已满足时能否跳过执行。

SKIP_IF_GOAL_SATISFIED：
    如果实时世界已经满足目标，可以跳过某些动作

REQUIRE_EXECUTION：
    即使目标看起来满足，也必须执行或展开

31.3 节点说明书和节点实例的区别

TaskNodeSpec 像：

“抓取操作”的函数定义

但它还不是本次抓取的进度。

32. TaskNodeRuntime：同一个节点这一次跑到哪了

32.1 人话定义

TaskNodeRuntime 是：

“这个节点在当前这次任务里，实际已经走到了哪里。”

32.2 字段逐项解释

TaskNodeRuntime(
    status=NodeStatus.RUNNING,
    phase="execute",
    attempts=1,
    repairs=0,
    expanded=False,
    output_artifacts=(),
    last_diagnostic=None,
    started_at=...,
    finished_at=None,
    adapter_state={},
    active_obligations=(),
)

status

整个节点的粗粒度状态：

pending
running
succeeded
failed
blocked
cancelled

phase

更细的进度。

enter
goal_check
preconditions
execute
verify
children
repair
reconciliation

例如：

status=running, phase=verify

表示节点仍在运行，但已经执行完动作，正在核实结果。

attempts

执行尝试计数。

第一次进入执行可能是 1，失败重试后变成 2。

repairs

这个节点已经经历了几次修复。

注意：

attempts != repairs

重试是重新尝试同一个操作；修复是增加一棵处理障碍或前置问题的子树。

expanded

复合节点是否已经请求过分解。

如果没有这个字段，内核可能每次 tick 都重复添加同一批子节点。

output_artifacts

该节点产出的工件 ID。

例如：

PlanPick -> pick_navigation-xxx, pick_plan-xxx

last_diagnostic

最近一次结构化失败信息。

它不是简单的异常字符串，而是可用于决定下一步的对象。

adapter_state

适配层需要保存的运行信息。

例如：

active_request_id
dispatch_attempt
外部 Harness 的关联信息

active_obligations

需要在后续阶段持续保持或检查的义务。

例如：

拿着杯子移动时，杯子必须持续被持有

32.3 为什么 Runtime 不能由 LLM 自己维护

如果模型自己写：

{"status": "succeeded"}

它可以在没有证据时宣称成功。

所以 Runtime 必须由 Kernel 根据真实执行和验证结果更新。

33. TaskEdge 和 GraphDelta：程序怎样长出新的分支

33.1 TaskEdge 是什么

边是两个节点之间的关系。

parent_id -> child_id

当前最重要的两种边：

child：
    正常任务分解关系

repair：
    失败之后挂载的修复关系

33.2 为什么 repair 不是普通 child

如果所有边都叫 child，看到下面的树时：

PlanTransfer
  └── RouteBlockedRepair

你无法知道：

RouteBlockedRepair 是原本就计划的步骤？
还是失败后临时添加的？

使用不同边类型后，历史和意图都清晰了。

33.3 GraphDelta 是什么

GraphDelta 是“我想向现有任务图增加哪些东西”的申请。

新增节点：
    AddNode(spec)

新增边：
    AddEdge(edge)

可选根 ID：
    root_id

33.4 为什么不让分解器直接调用 Store

如果分解器直接写 Store：

store.add_node(...)
store.add_edge(...)

它可能：

- 把节点挂到别的任务下；
- 添加越界边；
- 创建环；
- 把另一个根替换掉；
- 添加不可达节点；
- 和另一个写入者产生冲突。

现在的方式是：

分解器只返回 GraphDelta
Kernel 验证 GraphDelta
Kernel 原子挂载 GraphDelta
Kernel 写事件

33.5 GraphDelta 的验证像什么

它像数据库事务提交前的约束检查：

外键是否存在？
是否违反唯一性？
是否形成非法循环？
是否越过权限边界？

34. ExecutionFrame：为什么需要执行栈

34.1 没有栈会发生什么

假设任务结构是：

Place
  └── Pick
      └── ExecuteGrasp

如果没有执行栈，系统很难记录：

Place 正在等待 Pick
Pick 正在等待 ExecuteGrasp
ExecuteGrasp 正在 verify

34.2 栈的直观图

栈底
┌────────────────────────────┐
│ Place       / children     │
├────────────────────────────┤
│ Pick        / children     │
├────────────────────────────┤
│ ExecuteGrasp / verify      │ <- 当前栈顶
└────────────────────────────┘
栈顶

当前系统不是靠 Python 调用栈临时记住一切，而是把 ExecutionFrame 保存为 Store
的一部分。这对于暂停、观察和恢复很重要。

34.3 Frame 字段逐项解释

ExecutionFrame(
    node_id="ExecuteGrasp",
    phase=FramePhase.VERIFY,
    next_child_index=0,
    active_child_id=None,
    original_diagnostic=None,
    last_child_diagnostic=None,
)

node_id

这个栈帧属于哪个节点。

phase

这个节点当前处于生命周期的哪一段。

next_child_index

如果是 sequence，下一次要进入第几个子节点。

active_child_id

当前正在等待哪个子节点返回。

original_diagnostic

这个帧是否是由某次失败或修复进入的，以及原始诊断是什么。

last_child_diagnostic

最近一个子节点失败时带回来的诊断。

34.4 为什么不用一个 current_node_id

因为嵌套任务需要同时知道父节点上下文。

只记录当前节点：
    只知道 ExecuteGrasp

记录完整栈：
    知道它属于 Pick，Pick 又属于 Place

修复和返回时尤其需要父节点上下文。

35. 事件日志：把“发生过什么”从状态中分离出来

35.1 状态和事件的区别

状态回答：

现在是什么样？

事件回答：

过去发生过什么？

例如当前状态：

PlanTransfer = succeeded

但这不能告诉你它是否：

第一次失败后重试成功
先经历过一次修复
使用过两个不同的路线工件

事件日志可以保留这些过程。

35.2 一个事件的结构

TaskEvent(
    sequence=42,
    event_type="physical_completed",
    node_id=".../NavigateHeld",
    data={
        "request_id": "...",
        "artifact_refs": ["..."],
        "transaction_id": "...",
        "snapshot_ref": "world:6",
    },
)

sequence

事件的顺序号。

event_type

发生了什么类型的事。

node_id

哪个任务节点相关。

data

附加信息，例如工件、事务、诊断、快照引用。

35.3 为什么事件必须追加而不是覆盖

如果只保留最后状态：

节点最终 succeeded

你无法区分：

一次顺利成功

还是：

失败 -> 维修 -> 重试 -> 成功

机器人系统需要后者，因为故障和副作用会影响安全、维护和改进。

36. WorldSnapshot：把“现实”冻结成一张照片

36.1 为什么需要快照

现实世界一直在变化。规划器不能在一个没有时间边界的“活对象”上做计算：

规划计算第一半时，杯子在 A
规划计算第二半时，杯子被移动到 B

如果输入对象一直变化，规划结果无法解释。

WorldSnapshot 的作用是：

把某一时刻系统观察到的世界状态冻结下来，供选择、规划和验证读取。

36.2 快照的核心字段

WorldSnapshot(
    revision=7,
    frame_graph_revision=2,
    grid=...,
    robot=...,
    entities=...,
)

revision

整个世界快照的版本。

world:7

它表示第几次世界状态提交，不一定等于物理命令数。

frame_graph_revision

坐标系关系的版本。

如果相机、底盘或地图坐标关系变了，即使物体 ID 不变，原计划也可能失效。

grid

导航使用的栅格地图。

robot

机器人的观察状态。

entities

世界中已知的实体集合。

36.3 “快照不可变”是什么意思

得到 world:7 后，不能直接把它改成：

cup-red 的位置从 A 改成 B

正确做法是生成新的：

world:8

旧的 world:7 仍然保留，方便解释当时的决策。

36.4 快照不是传感器原始数据

要区分：

传感器原始数据：
    图像、点云、编码器读数

Observation：
    后端整理后的观察结果

WorldSnapshot：
    WorldModel 接收观察后形成的系统状态快照

快照是已经被世界模型组织过的可供业务读取的状态，不一定包含所有原始传感器数据。

37. EntityState：一个“物体”到底要描述什么

37.1 人话定义

EntityState 是系统对一个实体当前状态的描述。

实体可以是：

杯子
箱子
目标区域
障碍物
工具

37.2 字段逐项解释

EntityState(
    entity_id="movable-crate",
    kind="object",
    pose=Pose(...),
    radius=0.25,
    tags=frozenset({"crate"}),
    properties={
        "movable": True,
        "nav_obstacle": True,
        "arm_obstacle": True,
    },
    version=2,
)

entity_id

稳定标识。

稳定很重要，因为：

“这个物体”不能只靠颜色和位置识别

任务、工件、诊断和事件都需要引用它。

kind

实体类别。

object
region

类型错误会导致危险操作：

把目标区域当成可抓取对象
把杯子当成放置区域

pose

位姿，不只是二维坐标。

通常包含：

x
y
z
yaw
frame

对放置任务而言，朝向和高度也可能影响结果。

radius

参考几何尺寸。

当前参考模型使用半径进行简化碰撞和距离判断。生产模型通常需要更完整的几何体。

tags

语义标签。

red
cup
fragile
parking

标签适合做语义筛选，但不应该单独承担几何碰撞判断。

properties

领域属性。

示例：

movable：
    是否允许作为可移动对象

nav_obstacle：
    是否应该进入底盘导航占用图

arm_obstacle：
    是否应该进入机械臂碰撞检查

bounds：
    区域的边界

acceptance_radius：
    目标接受物体的距离容差

yaw_tolerance：
    目标允许的朝向误差

version

这个实体自身的变化版本。

如果只有别的实体移动，cup-red 的版本可能不变；如果杯子自己移动，版本增加。

37.3 为什么“位置”和“属性”都要有版本

计划可能依赖的不只是位置：

对象是否可移动
区域容差是多少
障碍物是否参与导航

属性变了，也应该让依赖这个属性的工件重新检查。

38. RobotState：机器人是一个复合实体

38.1 不能只保存底盘位置

对于移动操作臂，至少要知道：

底盘位置
机械臂关节
夹爪开闭状态
当前持有物
机器人状态代数

否则系统可能生成：

从错误的机械臂起始姿态开始的路径

38.2 字段逐项解释

base_pose

移动底盘的位置和朝向。

joints

当前关节配置。

它是机械臂路径连续性的起点。

gripper_open

夹爪是否打开。

它影响：

是否能抓取
是否正在持物
是否能释放

held_object_id

当前被认为夹持的对象 ID。

它是状态模型中的记录，不应该只靠“上一个抓取命令成功”推断。

state_epoch

机器人的状态变化代数。

可以把它想成：

机器人状态的版本号

如果机械臂移动过，基于旧关节状态生成的 PickPlan 可能过期。

39. Observation 和 WorldModel：现实怎样回到程序

39.1 Observation 是什么

Observation 是一次对现实的观察结果，通常由后端在动作后产生：

Observation(
    robot=RobotState(...),
    entities=(...),
    frame_graph_revision=...,
)

它回答：

动作后机器人现在在哪？
夹爪是什么状态？
手里是否有物体？
已知实体现在在哪里？
坐标系关系有没有变化？

39.2 WorldModel.ingest() 做什么

可以把它简化成：

收到 Observation
    ↓
比较机器人旧状态和新状态
    ↓
必要时增加 state_epoch
    ↓
比较每个实体旧状态和新状态
    ↓
必要时增加 entity.version
    ↓
保存新实体集合
    ↓
增加 WorldSnapshot.revision
    ↓
生成新的快照

39.3 为什么观察后不能直接改任务状态

观察只告诉系统现实是什么样。

它不应该自己决定：

所以任务成功

任务成功还需要把观察状态与节点的目标谓词比较。这个比较由语义和验证阶段完成。

这叫：

观察负责提供事实
验证负责解释事实
内核负责根据验证结果推进程序

40. 版本：为什么要同时有 world revision、entity version 和 state epoch

40.1 三种版本解决三个粒度的问题

WorldSnapshot.revision：
    整个世界快照变了几次

EntityState.version：
    某个实体自己变了几次

RobotState.state_epoch：
    机器人状态变了几次

40.2 举例

初始：

world:0
cup-red.version = 0
robot.state_epoch = 0

机器人移动底盘：

world:1
cup-red.version = 0
robot.state_epoch = 1

杯子被人挪动：

world:2
cup-red.version = 1
robot.state_epoch = 1

40.3 为什么不只用 world revision

如果只知道 world:2 和 world:0 不同，却不知道谁变了，系统只能粗暴地让所有计划重算。

实体和机器人粒度版本允许更精确地判断：

只依赖 cup-red 的工件要重算
只依赖 robot joints 的工件也要重算
与这两者无关的某些数据可以继续复用

41. Artifact：计划不是一句话，而是一件有出处的东西

41.1 人话定义

工件就是：

“某个能力根据某个世界快照算出来、可以被后续节点消费的计划结果。”

41.2 为什么叫工件

因为它不是最终目标，也不是原始输入，而是中间产物：

世界快照 + 规划算法
    -> NavigationPlan

绑定结果 + 抓取能力
    -> PickPlan

41.3 工件必须有出处

一个裸路径：

[(0.2,0.3), (0.3,0.4), (0.4,0.5)]

不够安全。它至少还要知道：

基于哪个世界？
地图是什么版本？
障碍物有哪些？
机器人当时在哪个状态？
碰撞模型是什么？
载荷是什么？

41.4 工件是不可变的

旧计划不能原地改成新计划：

错误：
    transfer_plan.path = new_path

正确：

保留旧 transfer_plan
发布新 transfer_plan
让 alias 指向新版本

41.5 为什么不可变很重要

不可变让系统能回答：

这次动作到底使用了哪一版路线？

如果旧工件被覆盖，历史就无法解释。

42. Freshness：如何判断工件还能不能用

42.1 人话定义

Freshness 就是“这个计划仍然适合当前现实吗？”

42.2 依赖比较

工件记录：

source_snapshot = world:3
entity:cup-red = 0
map = 1
robot = 2

当前快照：

world:4
entity:cup-red = 1
map = 1
robot = 2

结论：

cup-red 变了
所以依赖它的工件过期

42.3 为什么不只比较快照编号

world:4 比 world:3 新，不代表所有内容都变了。

系统真正关心的是：

我依赖的内容有没有变？

42.4 导航占用指纹

路线还依赖一组障碍物的整体占用情况。即使某个障碍物没有明显的单体字段变化，
新增障碍物也应该让路线失效。

因此导航计划可以记录：

nav_occupancy fingerprint

这个指纹把地图静态占用和参与导航的实体组合起来。

42.5 忽略集合

机器人运输一个物体时，那个物体的位置预期会随着机器人一起变化。

如果计划把被运输物体自己当作固定障碍物，就会错误地判定路线过期。

因此计划可以声明：

ignored_entity_ids = {cup-red}

但“忽略”不是完全不检查载荷。载荷的几何变化仍通过
payload_transform_hash 等字段单独检查。

43. ActionRequest：动作请求不是后端调用

43.1 人话定义

ActionRequest 是：

“物理技能希望运行时替它执行的一份规范化请求。”

它还不是最终的 SDK 调用。

43.2 请求示例

ActionRequest(
    request_id="tree:task-0001:ExecuteGrasp:attempt:1",
    action_name="ExecuteGrasp",
    commands=(
        ArmPathCommand(path=(...)),
        GripperCommand(close=True, object_id="cup-red"),
    ),
    resources=frozenset({"arm", "gripper"}),
    artifact_refs=("pick-plan-...",),
    preconditions=(
        PredicateFormula("base_near", {...}),
        PredicateFormula("joints_near", {...}),
    ),
)

43.3 request_id

这是一次物理请求的身份证。

如果网络超时，上层可能不确定请求是否已经派发。稳定 ID 可以让 Gateway 识别：

这是同一个请求，不要再执行一次

43.4 action_name

动作的业务名称。

NavigateToPickStance
ExecuteGrasp
NavigateHeld
ExecuteRelease

43.5 commands

真正需要后端执行的命令集合。

参考实现有：

NavigateCommand
ArmPathCommand
GripperCommand

注意：这些仍是规范化命令对象，不是厂商 SDK 对象。

43.6 resources

动作要占用哪些资源：

base
arm
gripper

如果一个动作需要 arm 和 gripper，运行时可以防止另一个动作同时抢用它们。

43.7 artifact_refs

请求明确声明自己消费了哪些工件。

这样运行时可以：

检查工件是否存在
检查工件类型
检查工件是否新鲜
记录动作与计划的关系

43.8 preconditions

请求级前置条件是最后一道快照保护。

即使任务节点之前检查过，动作真正发送前仍应重新检查，因为现实可能已经变化。

44. HarnessRuntime：为什么它像操作系统内核

44.1 类比

普通程序不能直接把磁盘控制器的电压打出去，而是通过操作系统系统调用。

同样，任务节点不能直接把任意命令打给机器人，而要经过：

HarnessRuntime

44.2 Runtime 负责哪些门禁

工件新鲜度
    ↓
当前快照谓词
    ↓
资源租约
    ↓
checkpoint
    ↓
后端执行
    ↓
逐命令观察
    ↓
提交或对账

44.3 为什么物理技能不能直接拿 Backend

如果技能拥有后端：

backend.execute(...)

它可以绕过：

freshness
guards
leases
transaction
observation

这会让系统出现不同的物理入口：

有些动作走安全链
有些动作偷偷绕过安全链

唯一入口的价值是让所有副作用都经过同样的审查。

45. Verifier：为什么“判断”必须和“执行”分开

45.1 判断和改变是两种完全不同的能力

执行：
    让杯子移动

判断：
    杯子现在是否在目标区？

如果同一个函数既移动又判断，调用者很难知道：

判断结果来自观察？
还是函数自己假定动作成功？

45.2 谓词是什么

谓词就是一个可以被判断真假的条件：

object_held(cup-red)
object_released(cup-red)
object_at(cup-red, drop-zone)
base_near(target_pose)
joints_near(target_joints)

45.3 object_at 的实际判断

大致过程：

读取对象位姿
读取目标位姿
计算三维距离
读取目标允许半径
检查距离是否在容差内
如果目标规定朝向，再检查 yaw 误差
返回真假和证据

它不是：

看到 ExecuteRelease 返回成功
就直接返回 true

45.4 证据为什么要和结果一起返回

只有 true 不够解释。系统还需要：

测得距离 = 0.07
容差 = 0.15
朝向误差 = 0.03
快照 = world:14

这样人和调试程序才能知道为什么成立。

46. Diagnostic：失败不是字符串

46.1 糟糕的错误

失败了

这句话不能驱动下一步。

46.2 结构化诊断

Diagnostic(
    code="ROUTE_BLOCKED",
    message="Transfer route is blocked",
    details={
        "blocker_id": "movable-crate",
        "snapshot_ref": "world:0",
    },
    retryable=True,
    repairable=True,
)

46.3 字段逐项解释

code

机器可识别的故障类别。

ROUTE_BLOCKED
STALE_PLAN
HOLD_LOST
OUTCOME_UNKNOWN
GUARD_FAILED

message

给人看的概括。

details

下一步修复需要的具体事实。

哪个障碍物？
哪一个请求？
哪一个工件？
哪一个快照？

retryable

同一个操作是否有意义地重试。

repairable

是否可能通过增加修复任务解决。

46.4 为什么两个布尔字段不能替代故障代码

retryable=true
repairable=true

仍然不知道应该怎么修复。

code 和 details 才能把诊断传给正确的处理器。

47. RepairProposal：修复方案也必须是程序

47.1 人话定义

修复提案是：

“针对某次失败，建议增加哪棵子树、从哪个节点进入，以及为什么这样修。”

47.2 典型结构

RepairProposal(
    delta=GraphDelta(...),
    entry_node_id=".../repair-0/route-blocked",
    rationale="...",
    invalidates_artifacts=(),
    persistent_obligations=(),
)

47.3 为什么修复器不能直接执行

修复器只了解“如何修”，但不应该拥有：

Store 写权限
机器人后端权限
最终状态裁决权

它提出建议，Kernel 审查和挂载。

47.4 为什么修复也要遵循同一套任务语义

如果主任务使用：

节点
前置条件
后置条件
观察
验证
事件

而修复任务只是隐藏脚本，那么系统会出现两个世界：

正常任务可追踪
修复任务不可追踪

当前设计让修复也成为任务树的一部分，因此修复可以继续递归、验证和审计。

48. reconciliation：物理世界不能假装支持回滚

48.1 软件回滚和物理回滚

软件中：

x = 1
x = 2
rollback -> x = 1

真实机器人中：

机械臂已经移动
通信突然断开

你不能仅靠内存把机械臂瞬移回去。

48.2 对账是什么意思

对账不是“把系统状态改成我希望的样子”，而是：

重新观察真实设备
比较计划状态和真实状态
确认哪些副作用已经发生
确认哪些没有发生
决定下一步

48.3 三种可能结果

确认成功：
    可以继续后续任务

确认失败：
    进入失败处理或修复

仍然不确定：
    暂停、人工介入或再次观察

48.4 为什么 OUTCOME_UNKNOWN 不能直接重试

如果上一条抓取请求其实已经成功，而系统因为超时再次发送抓取：

可能重复夹取
可能撞击物体
可能破坏当前持物状态

所以结果不明时必须先对账。

49. 一次 Place 任务的极细执行顺序

下面把正常任务拆成尽量小的步骤。

49.1 第 0 步：用户提交意图

把红杯子放到收纳区

此时系统只有意图，还没有：

绑定对象
抓取姿态
导航路线
物理命令

49.2 第 1 步：规范化

LLM 或 Planner Adapter 将话语变成：

action = place
object_selector = ...
destination_selector = ...

此时只回答：

任务是什么

还没有回答：

具体选中了哪个实体

49.3 第 2 步：编译根节点

编译器创建：

program/task-0001

它的 task_type 是 Place，operation_kind 是 decomposer。

内核初始化：

Store.root_id = program/task-0001
Runtime.status = pending
Stack = []
Events = []

49.4 第 3 步：进入根节点

Kernel push：

Frame(node=Place, phase=ENTER)

更新运行态：

Place.status = running
Place.attempts = 1

49.5 第 4 步：目标检查

内核先问：

任务目标是不是已经满足？

如果目标已经满足且节点允许跳过，可能直接成功。

对 Place 这样的结构节点，通常还需要继续展开，以保留结构和执行语义。

49.6 第 5 步：前置条件

检查：

输入参数是否存在
选择器是否合法
必要的世界信息是否存在

49.7 第 6 步：调用分解器

Place 是 decomposer 节点，分解器返回：

ResolveAndInspect
PlanPick
PlanTransfer
Pick
TransferHeld
Release
VerifyPlaceGoal

Kernel 验证 GraphDelta，一次性挂载正常 child 边。

49.8 第 7 步：进入 ResolveAndInspect

系统操作读取 WorldSnapshot。

object_selector -> cup-red
destination_selector -> drop-zone

发布 BindingArtifact。

节点成功的含义是：

绑定结果已经产生并且已存入工件存储

不是：

杯子已经移动

49.9 第 8 步：进入 PlanPick

读取绑定工件和当前世界。

调用：

底盘站位规划
逆运动学
机械臂路径规划
碰撞检查

发布：

pick_navigation
pick_plan

节点成功的含义是：

计划已经生成

不是：

机器人已经到达

49.10 第 9 步：进入 PlanTransfer

在空手或预期载荷模型下规划运输路线。

如果路线被挡：

返回 ROUTE_BLOCKED

此时进入故障处理，而不是直接进入 Pick。

49.11 第 10 步：进入 NavigateToPickStance

PhysicalSkill 消费 PickPlan 中引用的导航工件，生成 ActionRequest。

Runtime 检查：

导航工件是否新鲜
底盘资源是否可租
路线是否满足安全策略

通过后才交给后端。

49.12 第 11 步：动作后的观察

底盘移动后：

RobotBackend.observe()
    -> Observation
    -> WorldModel.ingest()
    -> world:1

Kernel 不应该仅依据“后端函数没有抛异常”就把节点标成成功。

49.13 第 12 步：进入 ExecuteGrasp

请求包含：

ArmPathCommand
GripperCommand(close=True)

前置条件可能包含：

底盘接近抓取站位
机械臂关节在预期起点

动作后得到新的观察：

gripper_open = false
held_object_id = cup-red

49.14 第 13 步：VerifyHeld

验证器判断：

object_held(cup-red)

只有此时，系统才有证据认为已经抓住。

49.15 第 14 步：持物运输

依次完成：

MoveToTransportPosture
NavigateHeld
VerifyPlacementReady

每个物理动作后都要更新世界并重新检查持物义务。

49.16 第 15 步：释放

ExecuteRelease 执行：

移动到放置姿态
打开夹爪

然后 VerifyReleased 检查：

held_object_id != cup-red

49.17 第 16 步：最终验证

VerifyPlaceGoal 检查：

object_at(cup-red, drop-zone)

最终成功不是由某个动作节点单独决定，而是由目标谓词和现实快照共同决定。

50. 一个“计划过期”的极细例子

50.1 计划生成

world:3
cup-red at (0.7, 0.4)
robot.state_epoch = 2

生成：

PickPlan P1
metadata:
    snapshot_ref = world:3
    entity:cup-red = 0
    arm = fingerprint(...)
    robot_state_epoch = 2

50.2 现实变化

人在机器人执行前把杯子移到了：

cup-red at (0.9, 0.5)

观察后：

world:4
cup-red.version = 1

50.3 发送前检查

FreshnessChecker 比较：

工件需要 entity:cup-red = 0
当前是 entity:cup-red = 1

返回：

fresh = false
diagnostic = STALE_PLAN

50.4 正确处理

不发送旧路径
旧计划保留用于审计
发布新的 PickPlan P2
让别名 pick_plan 指向 P2
重新进入物理节点

50.5 错误处理

不检查 freshness
直接执行 P1

可能导致：

机械臂伸向旧位置
撞击桌面
抓空
碰倒附近物体

这就是为什么“工件版本”不是文档字段，而是执行安全机制。

51. 一个“选择歧义”的极细例子

世界中有两个红杯子：

cup-red-left
cup-red-right

用户说：

把红杯子放到收纳区

51.1 系统不能直接猜

如果选择器只要求：

tags={red,cup}

那么两个都符合。

51.2 三种可选政策

政策 A：稳定规则自动选

按 stable_id 选字典序较小者

优点：

可重复

缺点：

未必符合人真正指的那个

政策 B：加入空间关系

选择 leftmost

优点：

更接近用户描述

缺点：

“左”相对于谁仍需明确

政策 C：请求澄清

你是指左边的红杯子，还是右边的红杯子？

这通常是风险较高任务的更好选择。

51.3 重要结论

任务内核只能执行已经结构化的选择结果。

语义歧义的解决属于意图层

内核负责保证：

一旦选择规则被接受，绑定过程可解释、可重复、可验证

52. 一个“动作结果不明”的极细例子

52.1 事件

ExecuteGrasp 已经向机器人发送
网络连接随后中断

系统现在不知道：

夹爪是否闭合
杯子是否被抓住
动作执行到哪一个路径点

52.2 不能做的事

直接标记 succeeded

或者：

直接再次发送 ExecuteGrasp

52.3 正确流程

记录 OUTCOME_UNKNOWN
保存 request_id 和 transaction_id
进入 reconciliation
重新调用观察能力
更新 WorldSnapshot

52.4 对账后的分支

观察到 held_object_id = cup-red
    -> 原目标已经部分完成
    -> 跳过重复抓取，继续运输

观察到 held_object_id = null
    -> 抓取没有成立
    -> 重新检查工件和站位
    -> 允许有限重试

观察仍然无法确认
    -> 暂停或人工介入

53. 为什么“移动障碍物”必须是任务

53.1 把它藏在规划器里会发生什么

假设 A* 内部做了这样的事：

发现箱子挡路
把箱子从占用图中删除
重新规划一条路线

数学上可能得到可行路径，但现实中箱子并没有移动。

53.2 正确的语义

箱子挡路
    -> 产生 ROUTE_BLOCKED
    -> 诊断识别 movable-crate
    -> 生成 Place(movable-crate, parking-zone)
    -> 真实执行搬箱子
    -> 观察箱子新位置
    -> 生成新世界快照
    -> 重新规划杯子任务

53.3 这相当于什么

在普通程序里，它类似：

try:
    transfer(cup)
except RouteBlocked:
    place(crate, parking_zone)
    transfer(cup)

区别是机器人系统把这个异常分支显式保存为任务树，并且每个物理动作都需要现实证据。

54. 读代码时的“谁读谁写”总表

54.1 主要对象所有权

| 对象 | 创建或发布者 | 主要读取者 | 主要写入者 |
| --- | --- | --- | --- |
| TaskProgram | LLM / Planner Adapter / 用户输入 | Compiler | 创建后不可变 |
| TaskNodeSpec | Compiler / Decomposer / Repair | Kernel / Inspector | Store 通过 Kernel |
| TaskNodeRuntime | Store 初始化 | Kernel / Inspector | Kernel |
| TaskEdge | GraphDelta 提案 | Kernel / Inspector | Kernel |
| ExecutionFrame | Kernel | Kernel / Inspector | Kernel |
| WorldSnapshot | WorldModel | Selector / Planner / Verifier | 由新观察生成新版本 |
| EntityState | 初始场景或 Observation | WorldModel / Planner | WorldModel 生成新状态 |
| Artifact | 规划或绑定操作 | Skills / Runtime / Inspector | 发布后不可变 |
| ActionRequest | PhysicalSkill | HarnessRuntime | 创建后不可变 |
| Observation | RobotBackend | WorldModel / Runtime | 新观察对象不可变 |
| Diagnostic | 操作、技能、语义或 Runtime | Kernel / RepairResolver | 创建后不可变 |
| RepairProposal | RepairResolver | Kernel | 创建后不可变 |

54.2 最关键的三条

谁都可以提议，但只有 Kernel 可以改任务树。
谁都可以计算计划，但只有 Runtime 可以触碰后端。
谁都可以报告观察，但只有 WorldModel 可以生成新的世界快照。

55. 当前系统中几个最容易误解的地方

55.1 误解：LLM 是系统的大脑，所以它控制全部流程

更准确：

LLM 提出高层意图和可能的策略
Kernel 按生命周期规则推进
Runtime 按权限和安全规则执行
Verifier 根据事实判定结果

LLM 不是唯一决策者。

55.2 误解：任务树就是待办清单

待办清单通常只记录：

未完成 / 已完成

任务树还记录：

控制结构
节点类型
执行阶段
前后置条件
尝试次数
修复关系
运行栈
事件

它更像可执行程序。

55.3 误解：工件就是缓存

缓存通常只关心：

有没有旧结果

工件还关心：

结果基于什么世界
依赖哪些版本
是否仍然适用
谁产生
谁消费

它是带契约的中间产物，不是随便放在内存里的缓存。

55.4 误解：观察只是日志

观察不是打印：

robot moved

它会改变 WorldModel 的事实版本，进而影响：

工件新鲜度
谓词验证
后续规划
修复判断

55.5 误解：修复就是重试

重试：

同一个节点，再做一次

修复：

先增加另一棵处理原因的子树
再回到原节点或继续原目标

56. 这套架构的“程序语义”可以怎样写

56.1 节点的语义

可以把一个节点理解为一个带条件的函数：

Node(node_spec, world, artifacts)
    -> success
    -> failure(diagnostic)
    -> graph_delta
    -> action_request

56.2 物理节点的特殊性

普通函数通常是：

输入 -> 输出

物理节点更像：

输入快照 + 计划工件
    -> ActionRequest
    -> 外部世界发生变化
    -> Observation
    -> 新快照
    -> 验证结果

所以它不是纯函数，必须被 Runtime 包裹。

56.3 任务树的状态转换

PENDING
    -> RUNNING
    -> SUCCEEDED

失败路径：

RUNNING
    -> FAILED
    -> RETRY
    -> RUNNING

修复路径：

RUNNING
    -> Diagnostic
    -> repair subtree
    -> RUNNING

物理不确定路径：

RUNNING
    -> OUTCOME_UNKNOWN
    -> RECONCILIATION
    -> SUCCEEDED / FAILED / BLOCKED

57. 为什么这不是“自然语言自修改代码”

它有一点像自修改程序：

运行时可以增加任务节点

但有四个重要限制：

1. 增量必须符合 GraphDelta 结构；
2. Kernel 必须验证作用域、可达性和无环性；
3. 新节点仍然只能使用已注册的节点处理器；
4. 物理动作仍必须经过 ActionRequest 和 Runtime。

因此更准确的说法是：

这是受限的、类型化的、领域专用运行时扩展，不是任意代码注入。

58. 对“自然语言驱动运行时”的最终分层判断

58.1 语言驱动了什么

任务目标
任务参数
语义选择
高层约束
失败解释和修复意图

58.2 语言没有直接驱动什么

电机电流
控制器采样周期
关节底层伺服
碰撞检测每一帧的实现
后端通信协议
真实世界事实的最终裁决

58.3 中间真正起作用的东西

TaskProgram
TaskNodeSpec
TaskNodeRuntime
GraphDelta
Artifact
ActionRequest
WorldSnapshot
Observation
Diagnostic
RepairProposal

所以“自然语言驱动”说的是入口和高层语义，不是说自然语言贯穿到底层每一个控制周期。

59. 你可以如何判断一个新模块是否放对了位置

遇到一个新需求时，问下面的问题。

问题一：它是在表达目标，还是在执行动作？

表达目标：
    TaskProgram / 节点参数

执行动作：
    PhysicalSkill -> ActionRequest -> Runtime

问题二：它需要读现实吗？

需要：
    通过 WorldModel / snapshot

不需要：
    不要偷偷读取 backend 内部状态

问题三：它会产生现实副作用吗？

会：
    必须经过 physical node 和 Runtime

不会：
    可以是 system operation 或 capability

问题四：它是在算结果，还是在改变结果？

算路径：
    capability -> artifact

改变世界：
    ActionRequest -> backend

问题五：失败后需要增加任务吗？

需要：
    Diagnostic -> RepairProposal -> GraphDelta

不需要：
    由普通 retry 或终止处理

60. 生产化时最重要的补课

从参考架构走向真实生产系统，最需要补的不是再加一个更大的模型，而是以下基础设施。

60.1 持久化

需要可靠保存：

任务树
运行态
执行栈
事件
工件
别名
事务

60.2 真实机器人对账

真实后端必须明确：

哪些动作可取消
哪些动作不可回滚
怎样获取可靠观察
结果不明时怎样恢复

60.3 感知不确定性

需要处理：

识别置信度
对象遮挡
多个候选
位置误差
传感器延迟

60.4 安全策略

需要把安全从参考几何模型扩展到：

真实碰撞几何
接触规则
速度和力限制
急停
人机协作区域
硬件互锁

60.5 多任务和多机器人

需要增加：

调度器
资源仲裁
任务优先级
抢占
冲突检测
跨树一致性

当前系统的串行任务边界是清晰的起点，但不是终点。

第一层：会说人话

你能解释：

62. 最后再回答一次核心问题

这套系统是不是把机器人的执行过程，

“自然语言驱动”——部分是

自然语言影响：

任务目标
对象选择
目标选择
约束
高层修复意图

后置条件

最终最严谨的结论是：

这套系统把自然语言目标编译成一个受约束的机器人领域运行时程序，并让这个程序在持续变化的物理世界中被解释、观察、验证和修复。它不是把自然语言直接翻译成电机指令，而是把自然语言放在了一个有类型、有权限、有证据、有恢复机制的执行系统入口。
